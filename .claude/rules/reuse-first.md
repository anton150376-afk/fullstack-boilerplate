# Сначала основа, потом GitHub, потом свой код

Правило владельца, действует во всех проектах на основе. Подгружается всегда
(без `paths`): касается любой новой работы, а не отдельного каталога.

Перед новой функцией, модулем, скриптом, компонентом, конфигом или
интеграцией:

1. **Основа.** Просмотреть этот репозиторий (`fullstack-boilerplate`):
   `packages/*`, `apps/*`, `docs/modules`, `ROADMAP.md`, `.claude/skills`,
   `.claude/rules`, воркфлоу CI. Подходящее есть — взять его.
2. **GitHub.** В основе нет — найти готовое решение (репозитории,
   библиотеки, примеры). Сравнить по критериям скилла `module-integration`:
   лицензия, статус проекта, активность, типизация, совместимость со стеком,
   размер, стоимость выхода.
3. **Согласование.** Найденное показать владельцу до подключения: что,
   откуда, лицензия, как будет адаптировано. Без согласования чужой код и
   новые зависимости не подключаются.
4. **Свой код.** Ничего подходящего не нашли — пишем сами. Нашли — адаптируем
   под проект: переименовываем, приводим к правилам основы, покрываем
   тестами.
5. **Возврат в основу.** Общее решение, которого в основе нет, предложить
   владельцу вернуть в основу.

Перед реализацией в ответе одна строка: «в основе: …; на GitHub: …;
решение: …». Пропускать шаги 1–3 ради скорости нельзя.

Согласование не откладывает работу, если спросить некого: действует
порядок из раздела «Когда неопределённость» в `AGENTS.md` (вариант с
наименьшими необратимыми последствиями, ADR со статусом «требует
подтверждения»).
