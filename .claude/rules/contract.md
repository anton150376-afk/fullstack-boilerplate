# Контракт API

- Схема добавляется **раньше** обработчика на сервере — контракт описывает
  намерение, реализация его закрывает, не наоборот.
- Типы выводятся из Zod-схем (`z.infer`), рукописных дублирующих
  интерфейсов не заводить.
- Изменение контракта обязано прийти в том же коммите с правкой клиента
  (`packages/api-client` и оба потребителя, которых оно касается) и с
  правкой документации — иначе гейт падает (жёсткое правило раздела 3.5
  задания).
- Раскладка по доменам (`auth.ts`, `health.ts`, `files.ts`, …) — новый
  домен добавляет свой файл, не трогая существующие.
- Поле формы помечается видом через `.meta({ widget, options })` — это
  читает конструктор админки (`packages/admin-kit`, Фаза 8).
- Ломающие изменения разрешены, пока нет внешних потребителей, но
  перечисляются в журнале изменений контракта с датой и причиной.
- Подробнее — `docs/packages/contract.md` (появится в Фазе 5).
