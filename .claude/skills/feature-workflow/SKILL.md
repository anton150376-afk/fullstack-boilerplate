# feature-workflow

Процедура для любой прикладной задачи. Правила, на которые она опирается,
не повторяются здесь — смотреть `.claude/rules/*.md` по месту работы.

## Шаги

1. **Рамка.** Сформулировать, что входит в задачу и что явно нет. Если
   задача меняет контракт API — читать `.claude/rules/contract.md`.
2. **Схема раньше кода.** Если задача трогает `packages/contract` —
   сначала схема, потом обработчик (см. `contract.md`).
3. **Тест раньше или вместе с реализацией.** Падающий тест, описывающий
   ожидаемое поведение, затем код, который его делает зелёным.
4. **Реализация.** Следовать правилу, соответствующему затронутому
   каталогу (`.claude/rules/`).
5. **Документация в том же коммите.** Новый пакет/приложение — страница в
   `docs/`; изменённый контракт или команда — правка существующей
   страницы. Критерий: `pnpm check:docs` зелёный.
6. **Бэклог.** Всё отложенное или обнаруженное как риск — пункт
   `docs/BACKLOG.md` с критерием закрытия, в этом же коммите.
7. **Гейт.** `pnpm verify`. Красный шаг — чинить, а не комментировать
   проверку и не использовать `GATE_ALLOW` без реального основания.
8. **Коммит.** Conventional Commits (`.claude/rules/git.md`), одна
   связная работа на коммит/pull request.

## Когда остановиться

Раздел 2.3 `docs/architecture/original-task.md` — платный сервис, смена
публичного контракта чужого кода, противоречивое требование.
