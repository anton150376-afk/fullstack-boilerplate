# ROADMAP

Модули, которые решение закладывает местами интеграции, но не
реализует (раздел "Фаза 11" задания). Каждый этап выполняется по
процедуре раздела 15 задания — скилл `module-integration`
(`.claude/skills/module-integration/SKILL.md`), не отдельно для
каждого модуля. Кандидаты и статусы ниже собраны на 2026-10-07 (дата
исходного задания) — **статус каждого кандидата проверяется заново
на дату выполнения этапа**, не по памяти: за 2025–2026 годы несколько
библиотек в этой области были свёрнуты, перелицензированы или куплены
(примеры — в самих модулях ниже).

Уже заложено (раздел 11 задания, исключение из правила «не
реализовывать раньше времени» — эти три точки существуют начиная с
фаз, где возникла первая реальная потребность в них, не ради этого
ROADMAP):

- **Обработка `401` в клиенте** — `CreateApiClientOptions.onUnauthorized`
  (`packages/api-client/src/transport.ts`, Фаза 5).
- **Место для набора прав в данных текущего пользователя** —
  `PermissionsProvider` (`packages/admin-kit/src/permissions/provider.ts`,
  Фаза 8): `createAllowAllPermissions`/`createDenyAllPermissions`/`createAllowListPermissions`
  как временные реализации, `AdminLayout`/`DataTable`/`ResourceForm`
  держат только сигнатуру `can(permission)` — M2 подключает настоящую
  реализацию без правок экранов.
- **Адаптеры приёмников в devtools** — `BugReportReceiver`
  (`packages/devtools`, Фаза 9): `createFileReceiver`/`createGithubReceiver`/`createApiReceiver`/`createHttpBugReportReceiver`.

## M1. Аутентификация

### M1.1 Базовый токен — своя реализация

- **Статус:** не начат
- **Зачем:** вход и сессия — основа для всего, что проверяет "кто это".
- **Входит:** непрозрачный токен доступа (в базе — только хеш); продление
  сессии за счёт активности со скользящим окном; абсолютный предел
  жизни сессии, после которого нужен повторный вход; отзыв отдельной
  сессии и всех сессий пользователя; список активных сессий (устройство,
  время последней активности); ограничение частоты попыток входа; кеш
  проверки токена в Redis по хешу.
- **Не входит:** телефон/SMS, одноразовые коды, второй фактор, внешние
  поставщики (M1.2); роли и права (M2).
- **Точки интеграции:** server — модуль и guard; `api-client` —
  хранилище токена и обработка `401` (уже заложено, см. выше); веб и
  мобильное — вход, выход, восстановление сессии при запуске.
- **Кандидаты на анализ:** своя реализация (выбрана для этого этапа —
  better-auth на дату задания хранит токен сессии в открытом виде и не
  даёт абсолютного предела жизни сессии при скользящем продлении,
  проверить статус заново), `@nestjs/passport` как основа для своего.
  Проверить статус заново: Lucia свёрнута в учебное пособие (март 2025) — не брать, если за это время не появилось наследника.
- **Критерии приёмки:** вход выдаёт токен; обращение к защищённому
  маршруту продлевает сессию; по истечении абсолютного предела
  требуется повторный вход; отзыв сессии немедленно закрывает доступ;
  в базе нет токена в открытом виде; веб и мобильное переживают
  перезапуск с сохранённой сессией; всё покрыто тестами.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M1.2 Рост способов входа

- **Статус:** не начат
- **Зачем:** телефон/SMS, одноразовые коды, второй фактор, внешние
  поставщики — пользователю нужен способ входа, подходящий именно ему.
- **Входит:** телефон с кодом из SMS, одноразовые коды, TOTP, восстановление
  доступа, внешние поставщики — каждый способ как провайдер к единому
  ядру сессий M1.1.
- **Не входит:** собственное ядро сессий (уже есть из M1.1 — на этом
  этапе становится осмысленным переход на библиотеку, не писать заново).
- **Точки интеграции:** те же, что M1.1, плюс экраны выбора способа
  входа в веб и мобильном.
- **Кандидаты на анализ:** better-auth (плагины под второй фактор,
  одноразовые коды, телефон, passkey; официальный пакет для Expo;
  свой отправщик SMS) — решение о переходе принимается ADR этапа с
  учётом расхождений M1.1. Проверить статус заново: Auth.js влился в
  Better Auth, next-auth v5 на дату задания третий год в бете.
- **Критерии приёмки:** каждый новый способ входа заводит ту же сессию,
  что M1.1 (один токен, один список активных сессий); отказ одного
  способа не ломает остальные; тесты на каждый способ отдельно.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

## M2. Права и роли

### M2.1 Ядро

- **Статус:** не начат
- **Зачем:** право — строка `ресурс:действие`; роль — именованный
  набор прав; без этого ядра M2.2–M2.4 не на чём стоять.
- **Входит:** таблицы `permissions`/`roles`/`role_permissions`/`user_roles`/`user_permissions`;
  вычисление плоского набора прав при входе (прямое назначение + роли,
  объединение, явные правила для запретов); кеш в Redis с версионным
  счётчиком для сброса; guard и декораторы на сервере; сервис
  `can(user, 'ресурс:действие', объект?)`.
- **Не входит:** права на экземпляры объектов (M2.3); управление через
  API (M2.2); отражение в интерфейсах сверх плоского набора (M2.4).
- **Точки интеграции:** server — guard, декораторы, сервис `can()`;
  `PermissionsProvider` (уже заложено, см. выше) получает настоящую
  реализацию вместо `createAllowAllPermissions`/`createDenyAllPermissions`/`createAllowListPermissions`.
- **Кандидаты на анализ:** CASL 7.0.1 (MIT, умеет шарить правила на
  клиент — подходит под модель «роли как наборы»), node-casbin
  (неудобен для ограничения интерфейса), Cerbos/OpenFGA/SpiceDB (сетевой
  вызов в горячий путь или навязанная модель отношений — брать только
  при транзитивных связях вида организация → команда → проект).
  Проверить статус заново: Oso в опенсорсе объявлена устаревшей, Permify
  куплена FusionAuth и распространяется под AGPL (на дату задания).
- **Критерии приёмки:** запрос без права получает 403; изменение прав
  влияет на доступ без перезапуска; кеш сбрасывается при изменении;
  набор прав приходит в данных текущего пользователя; тесты на
  объединение прав из нескольких ролей и на прямое назначение.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M2.2 Управление ролями и правами через API

- **Статус:** не начат
- **Зачем:** без API роли и права редактируются только миграциями.
- **Входит:** CRUD по ролям, назначение прав роли, назначение ролей и
  прямых прав пользователю — через `packages/contract`.
- **Не входит:** интерфейс управления (может появиться как ресурс
  `admin-kit`, отдельным решением на этапе).
- **Точки интеграции:** server — контроллер и сервис; `packages/contract` —
  схема; при наличии экрана — ресурс `admin-kit`.
- **Кандидаты на анализ:** нет — прямое следствие M2.1, без выбора
  между вариантами.
- **Критерии приёмки:** изменение через API отражается в `can()` без
  перезапуска; попытка назначить несуществующее право отклоняется;
  тесты на контракт.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M2.3 Права на экземпляры объектов

- **Статус:** не начат
- **Зачем:** плоского набора прав недостаточно, когда право зависит от
  конкретной записи ("свои заметки", не "все заметки").
- **Входит:** полиморфная привязка (`subject_type`, `subject_id`,
  `user_id`, `permission`), выражается условиями CASL.
- **Не входит:** решение о том, нужен ли этот этап вообще раньше, чем
  возникнет реальная потребность в правах на экземпляры — ADR этапа
  M2.1 решает, включать ли это в более ранний этап (сильно влияет на
  модель данных и стоимость проверки).
- **Точки интеграции:** server — расширение `can()` объектом; CASL
  (если выбран в M2.1).
- **Кандидаты на анализ:** см. M2.1 — тот же выбор библиотеки.
- **Критерии приёмки:** `can(user, 'notes:edit', note)` учитывает
  владение записью; тесты на разных владельцев одного типа объекта.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M2.4 Отражение прав в интерфейсах

- **Статус:** не начат
- **Зачем:** интерфейс не должен предлагать действие, на которое нет права.
- **Входит:** плоский набор прав в данных текущего пользователя; на
  клиенте — функция проверки и компонент-ограничитель (парный для веба
  и мобильного).
- **Не входит:** серверная проверка (уже есть из M2.1 — клиентская
  проверка только скрывает элементы интерфейса, не заменяет guard).
- **Точки интеграции:** `api-client` — данные текущего пользователя;
  `ui-web`/`ui-native` — компонент-ограничитель; `admin-kit` —
  `PermissionsProvider` получает реализацию поверх настоящих прав.
- **Кандидаты на анализ:** нет — прямое следствие M2.1.
- **Критерии приёмки:** элемент интерфейса без права не рендерится ни
  в вебе, ни в мобильном; смена прав без перезапуска приложения
  отражается при следующем запросе данных пользователя.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

## M3. Биллинг

### M3.1 Ядро без поставщиков

- **Статус:** не начат
- **Зачем:** оркестратор платежей в API, не завязанный на конкретного
  поставщика — **факт, определяющий весь модуль:** Stripe, Paddle и
  Polar в роли продавца-посредника для российского юридического лица
  недоступны, поэтому первым реализуется российский поставщик (M3.2).
- **Входит:** сущности (продукт, план, цена, подписка, счёт, платёж,
  право на функциональность по оплате, журнал событий); интерфейс
  адаптера (`createPayment`, `chargeSavedMethod`, `parseWebhook` с
  обязательным перезапросом платежа по id после, `getPayment`/`refund`);
  тестовый адаптер; своя таблица прав на функциональность
  (`user_id`, `feature`, `source`, `expires_at`), в которую пишут
  только обработчики подтверждённых событий.
- **Не входит:** реальные поставщики (M3.2–M3.4); движок подписок (M3.5).
- **Точки интеграции:** `packages/contract` — публичный интерфейс
  адаптера; server — оркестратор, журнал событий, таблица прав.
- **Кандидаты на анализ:** нет на этом этапе — ядро без поставщика по определению.
- **Критерии приёмки:** состояние платежа переживает повторную доставку
  уведомления; расхождение с поставщиком обнаруживается сверкой; право
  на функциональность выдаётся и отзывается по состоянию оплаты; тесты
  на тестовом адаптере покрывают успех, отказ, повтор и возврат.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M3.2 YooKassa

- **Статус:** не начат
- **Зачем:** первый реальный поставщик для российского юридического лица.
- **Входит:** REST-адаптер напрямую (официального SDK для Node нет);
  ключ идемпотентности заголовком; basic-авторизация; сохранение метода
  оплаты для повторных списаний; данные чека по 54-ФЗ.
- **Не входит:** другие поставщики (M3.3–M3.4).
- **Точки интеграции:** реализация интерфейса адаптера из M3.1.
- **Кандидаты на анализ:** нет — REST напрямую, решение зафиксировано заданием.
- **Критерии приёмки:** те же, что M3.1, плюс — **уведомления
  подтверждаются allowlist'ом по IP, не подписью** (проверено тестом на
  отклонение запроса не из allowlist); платёж обязательно перезапрашивается
  по идентификатору перед любым действием (не доверять телу webhook).
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M3.3 T-Bank

- **Статус:** не начат
- **Зачем:** второй адаптер — резерв и покрытие эквайринга, СБП, чеков.
- **Входит:** интеграция через `@jfkz/tinkoff-payment-sdk` (версия
  зафиксирована или вендорится — проверить актуальность перед началом).
- **Не входит:** замена YooKassa — оба поставщика работают параллельно.
- **Точки интеграции:** реализация интерфейса адаптера из M3.1.
- **Кандидаты на анализ:** `@jfkz/tinkoff-payment-sdk` — проверить
  статус пакета заново (лицензия, активность, автобусный фактор) перед
  началом этапа, не доверять версии из задания.
- **Критерии приёмки:** те же, что M3.1, на адаптере T-Bank.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M3.4 Покупки внутри приложений

- **Статус:** не начат
- **Зачем:** мобильные подписки/покупки через App Store и Google Play.
- **Входит:** выбор между RevenueCat (бесплатно до порога оборота,
  далее процент; требует development build) и `expo-iap` без
  посредника (проверка чеков, состояние прав и сверка продлений —
  самостоятельно). Отдельно проверить доступность выплат Apple/Google
  на аккаунт разработчика — не решается кодом.
- **Не входит:** веб-платежи (покрыты M3.2/M3.3).
- **Точки интеграции:** мобильное приложение; таблица прав из M3.1.
- **Кандидаты на анализ:** RevenueCat, `expo-iap` (репозиторий переехал
  в монорепозиторий `openiap` — проверить текущее состояние перед
  началом).
- **Критерии приёмки:** покупка отражается в таблице прав; восстановление
  покупок работает после переустановки; тесты на подтверждённую и
  отклонённую покупку.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M3.5 Подписки

- **Статус:** не начат
- **Зачем:** ни один российский поставщик не даёт движка подписок.
- **Входит:** свой планировщик продлений на BullMQ поверх
  `chargeSavedMethod` из M3.1, журнал попыток, обработка отказов.
- **Не входит:** выбор поставщика (уже сделан в M3.1–M3.3).
- **Точки интеграции:** BullMQ (уже есть из Фазы 4); таблица подписок из M3.1.
- **Кандидаты на анализ:** нет — свой планировщик, решение зафиксировано заданием.
- **Критерии приёмки:** продление запускается по расписанию; отказ
  продления не теряется (видим в журнале, есть повтор); тесты на
  успешное и неуспешное продление.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

## M4. Уведомления

### M4.1 Ядро и канал внутри приложения

- **Статус:** не начат
- **Зачем:** событие создаёт уведомление по шаблону без привязки к
  конкретному каналу доставки.
- **Входит:** таблицы шаблонов, уведомлений, доставок (канал, статус,
  идентификатор у поставщика, попытки), настроек получателя и тихих
  часов; точка входа `notify(userId, templateKey, payload, { dedupKey })`
  (разрешить настройки → учесть тихие часы → уникальный индекс по
  ключу дедупликации → задача BullMQ на канал); интерфейс адаптера
  канала (`send(recipient, rendered)`, `parseStatusWebhook(raw)`);
  канал "внутри приложения".
- **Не входит:** push/SMS/email (M4.2–M4.4); настройки получателя и
  тихие часы как отдельный этап (M4.5 — здесь только таблицы, не
  полноценный UI).
- **Точки интеграции:** server — точка входа `notify()`, BullMQ; веб и
  мобильное — отображение уведомлений внутри приложения.
- **Кандидаты на анализ:** своё ядро (выбрано — Novu тянет MongoDB и
  пять сервисов при самостоятельном развёртывании, облачная версия —
  подписка в валюте; проверить статус заново перед началом).
- **Критерии приёмки:** событие создаёт запись; доставка идёт через
  очередь с повторами; журнал содержит результат по каждому каналу;
  уведомление внутри приложения видно в вебе и в мобильном; тесты
  покрывают повтор, отказ канала и дедупликацию.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M4.2 Push

- **Статус:** не начат
- **Зачем:** уведомления на мобильные устройства без экрана приложения.
- **Входит:** служба уведомлений Expo (service-account JSON для FCM,
  ключ `.p8` для APNs); откат на канал внутри приложения и SMS, когда
  FCM не доезжает (устройства без сервисов Google — RuStore, Huawei).
- **Не входит:** прямая работа с FCM/APNs напрямую, минуя Expo (отдельное
  решение при большом объёме или необходимости тонко управлять
  приоритетами — не на этом этапе).
- **Точки интеграции:** реализация интерфейса адаптера канала из M4.1;
  мобильное приложение — регистрация токена устройства.
- **Кандидаты на анализ:** служба уведомлений Expo — зафиксирована
  заданием, альтернатива (прямая работа с FCM/APNs) рассматривается
  только при конкретной причине.
- **Критерии приёмки:** push доходит на устройство с сервисами Google;
  откат на внутренний канал срабатывает при недоставке; тест на оба пути.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M4.3 SMS

- **Статус:** не начат
- **Зачем:** канал доставки без приложения и без интернета на стороне получателя.
- **Входит:** своя обёртка (порядка сотни строк) под один из российских
  шлюзов (SMS.ru, SMSC.ru, SMS Aero) — у них простые HTTP-интерфейсы,
  существующие npm-обёртки крошечные и без релизов.
- **Не входит:** Twilio — для российских номеров практически неприменим
  (двусторонние SMS не поддерживаются, регистрация буквенных имён
  отправителя закрыта с июля 2024 на дату задания — проверить, не
  изменилось ли).
- **Точки интеграции:** реализация интерфейса адаптера канала из M4.1.
- **Кандидаты на анализ:** SMS.ru, SMSC.ru, SMS Aero — сравнить по
  критериям раздела 15.2 на дату этапа (не по памяти задания).
- **Критерии приёмки:** SMS отправляется и доставка подтверждается
  статусом; отказ шлюза попадает в журнал с повтором; тест на успех и отказ.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M4.4 Электронная почта

- **Статус:** не начат
- **Зачем:** канал для получателей без телефона/push или для документов.
- **Входит:** Resend или Postmark как первый адаптер.
- **Не входит:** Unisender Go на этом этапе — закладывается вторым
  адаптером только если доставляемость в российские ящики (Mail.ru,
  Яндекс) у первого окажется низкой.
- **Точки интеграции:** реализация интерфейса адаптера канала из M4.1.
- **Кандидаты на анализ:** Resend, Postmark, Unisender Go (резерв) —
  сравнить по критериям раздела 15.2, включая платёжную доступность из России.
- **Критерии приёмки:** письмо отправляется и статус доставки
  обновляется по webhook; отказ попадает в журнал; тест на успех и отказ.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M4.5 Настройки получателя, тихие часы, ограничение частоты

- **Статус:** не начат
- **Зачем:** получатель решает, как и когда его уведомлять — без этого
  M4.1's таблицы настроек не имеют интерфейса управления.
- **Входит:** экран настроек получателя в вебе и мобильном (парные
  компоненты); ограничение частоты уведомлений одного типа.
- **Не входит:** сами таблицы (уже есть из M4.1).
- **Точки интеграции:** `ui-web`/`ui-native` — экран настроек;
  `packages/contract` — схема настроек.
- **Кандидаты на анализ:** нет — интерфейс к уже существующим таблицам.
- **Критерии приёмки:** изменение настроек в вебе отражается в мобильном
  при следующей синхронизации; тихие часы откладывают уведомление, не
  выбрасывают его; тест на ограничение частоты.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

## M5. Наблюдаемость

### M5.1 Сбор падений

- **Статус:** не начат
- **Зачем:** автоматический сбор падений дополняет багрепорт из Фазы 9
  (там человек описывает замеченное, здесь машина ловит стектрейс).
- **Входит:** Sentry либо самостоятельно развёрнутый GlitchTip в трёх
  приложениях (server, web, mobile) с привязкой к `request-id`
  (та же цепочка, что `docs/guides/bug-reports.md`).
- **Не входит:** OpenTelemetry (M5.2); панель здоровья (M5.3).
- **Точки интеграции:** все три приложения — перехват исключений;
  `request-id` уже проставляется (Фаза 4/5/9).
- **Кандидаты на анализ:** Sentry (облако или самостоятельный хостинг),
  GlitchTip (самостоятельный хостинг, Sentry-совместимый протокол,
  меньше возможностей) — сравнить автономность и стоимость выхода по
  критериям раздела 15.2.
- **Критерии приёмки:** необработанное исключение в любом из трёх
  приложений попадает в систему сбора с `request-id`; тест на
  перехват в каждом приложении.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M5.2 OpenTelemetry

- **Статус:** не начат
- **Зачем:** шов трассировки заложен в Фазе 4 (`@opentelemetry/api`,
  ядро 2.x), но без автоинструментаций и экспортёра — они ещё в версиях 0.x.
- **Входит:** включение автоинструментаций и экспортёра поверх
  существующего шва, когда они выйдут из версий 0.x (проверить статус
  заново перед началом — не предполагать по дате задания).
- **Не входит:** замена самого шва — он уже на стабильном ядре (ADR-0001).
- **Точки интеграции:** `apps/server/src/observability/tracing.ts`
  (шов из Фазы 4) — только включение `OTEL_ENABLED` и подключение
  автоинструментаций/экспортёра.
- **Кандидаты на анализ:** конкретные пакеты автоинструментаций и
  экспортёра выбираются на дату этапа — версии 0.x на дату задания
  делают любой выбор сейчас временным.
- **Критерии приёмки:** трассировка видна end-to-end (клиент → сервер
  → очередь) при `OTEL_ENABLED=true`; выключение флагом не меняет
  поведение приложения.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M5.3 Панель здоровья и журналов

- **Статус:** не начат
- **Зачем:** видимость состояния развёрнутой системы — не то же самое,
  что сайт документации из Фазы 10 (другой читатель, другой срок жизни данных).
- **Входит:** панель с состоянием `/health/live`/`/health/ready` всех
  приложений, недавними ошибками из M5.1, основными метриками.
- **Не входит:** карта модулей и документация (это сайт из Фазы 10).
- **Точки интеграции:** health-эндпоинты (Фаза 4); данные M5.1.
- **Кандидаты на анализ:** готовая панель (Grafana и подобные) против
  своей страницы — сравнить по автономности и стоимости внедрения.
- **Критерии приёмки:** падение `/health/ready` любого приложения видно
  на панели без захода в логи вручную.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

## M6. Развитие заложенного

### M6.1 Журнал действий с настоящим актором

- **Статус:** не начат
- **Зачем:** просмотр журнала есть в конструкторе админки с Фазы 8, но
  запись ведётся с заглушкой `"system"` — до M1 настоящего "кто" взять негде.
- **Входит:** привязка событий журнала к пользователю и сессии из M1;
  хранение адреса и устройства; политика срока хранения записей.
- **Не входит:** сам журнал и его просмотр — уже есть (`apps/server/src/audit-log`, Фаза 8).
- **Точки интеграции:** `AuditLogService.record` (Фаза 8) — замена
  актора-заглушки на данные из сессии M1.
- **Кандидаты на анализ:** нет — прямое следствие M1, без выбора библиотеки.
- **Критерии приёмки:** запись журнала после M1 содержит настоящего
  пользователя, не `"system"`; старые записи с заглушкой не переписываются.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M6.2 Проверка файлов и обработка изображений

- **Статус:** не начат
- **Зачем:** точки подключения оставлены в Фазе 4, сама проверка и
  обработка — нет.
- **Входит:** проверка файлов на вредоносное содержимое (ClamAV
  отдельным процессом, задачей в очереди за адаптером); обработка
  изображений (производные размеры через `sharp`, строго на воркере,
  не в обработчике запроса).
- **Не входит:** сама загрузка файлов — уже есть (`packages/storage`, Фаза 4).
- **Точки интеграции:** `apps/server/src/queue` — новая задача после
  подтверждения загрузки; `packages/storage` — адаптер не меняется.
- **Кандидаты на анализ:** ClamAV (единственный практичный вариант для
  самостоятельного развёртывания) — проверить образ и способ запуска
  на дату этапа; `sharp` — стабильный выбор, проверить версию.
- **Критерии приёмки:** заражённый тестовый файл помечается и не
  раздаётся; изображение получает производные размеры без блокировки
  запроса подтверждения загрузки; тесты на оба пути.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M6.3 Возобновляемая загрузка

- **Статус:** не начат
- **Зачем:** крупные файлы — если понадобится (не предполагается заранее).
- **Входит:** возобновление прерванной загрузки крупного файла.
- **Не входит:** загрузка файлов обычного размера — уже работает (Фаза 4).
- **Точки интеграции:** `packages/storage` — расширение адаптера.
- **Кандидаты на анализ:** протокол возобновляемой загрузки S3-совместимого
  хранилища (multipart upload) — проверить поддержку у Garage и у
  целевого поставщика в проде на дату этапа.
- **Критерии приёмки:** прерванная на середине загрузка крупного файла
  продолжается без повторной передачи уже переданных частей.
- **Процедура:** раздел 15 задания, скилл `module-integration`.

### M6.4 Приём отзывов от пользователей в продакшене

- **Статус:** не начат
- **Зачем:** развитие задела из Фазы 9.4 — урезанная форма отзыва уже
  поддержана ядром (`ProductionFeedback` в `packages/devtools`), но
  модерации, привязки к аккаунту и ответов нет.
- **Входит:** модерация отзывов; привязка к аккаунту (после M1); ответы
  на отзыв; отдельный, всегда доступный серверный маршрут (не
  `/dev/bug-reports`, тот — только dev/test).
- **Не входит:** сбор контекста (логи, трейл, снимки) — продакшен-форма
  намеренно урезана (раздел "Фаза 9" задания, пункт 9.4).
- **Точки интеграции:** `packages/devtools` — `ProductionFeedback` уже
  определён; новый серверный маршрут; `ui-web`/`ui-native` — форма под
  отдельным флагом (заготовка кнопки — Фаза 9).
- **Кандидаты на анализ:** нет на этом этапе — развитие уже выбранной
  формы данных, не новая библиотека.
- **Критерии приёмки:** отзыв из продакшена виден в панели модерации;
  привязка к аккаунту работает после M1; ответ на отзыв доходит до
  пользователя (через M4, если уже готов, иначе — в интерфейсе).
- **Процедура:** раздел 15 задания, скилл `module-integration`.

## M7. Прочее

Отдельные пункты без привязки к конкретному модулю — проверяются по
готовности повода, не по графику.

- **TanStack AI** (`@tanstack/ai`) — подключение, когда пакет выйдет из
  версий 0.x (на дату задания ломающие изменения случаются между минорами).
- **Переход на oRPC v2** — когда ветка станет стабильной (на дату
  Фазы 5 задания — `2.0.0-beta.42`, проект на v1 `1.15.5`, `D4`).
- **Переход на TypeScript 7** — когда `typescript-eslint` перестанет
  предупреждать о несовместимости (на дату Фазы 1 задания — "not
  planned" до стабильного программного API).
- **Оценка Uniwind Pro** — если понадобятся `hover:`/`group-*` на
  native (бесплатная ветка их не поддерживает, раздел "Фаза 7" задания,
  пункт 3).
- **Пересмотр выбора формы и таблицы** — TanStack Form стоит проверить
  заново, когда появится поддержка React Native и закроется вопрос с
  Zod 4 (сейчас — react-hook-form + `@hookform/resolvers/zod`, Фаза 8);
  примеры таблиц shadcn для TanStack Table v9 — когда появятся (сейчас
  — своя `DataTable` без примера shadcn, Фаза 8).
