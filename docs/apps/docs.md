> **Зачем читать:** как устроен сайт документации и что в нём сгенерировано, а что написано руками.
> **Кому:** кто меняет структуру `docs/` или добавляет новую сгенерированную страницу.
> **Последняя проверка:** 2026-10-09.

## Что это

`apps/docs` (раздел "Фаза 10" задания, пункт 10.3) — тонкая обёртка над
VitePress: сам пакет не хранит содержимого, он настраивает сборку и
генерирует несколько сводных страниц. Реальный контент — обычный
`docs/` в корне репозитория, тот же, что читают люди и агенты
напрямую, без сайта.

## Как устроено

- `apps/docs/.vitepress/config.ts` — конфиг VitePress. `srcDir: "../../docs"`
  указывает на настоящий `docs/` — страницы порождаются из репозитория,
  не копируются и не пишутся заново для сайта.
- `apps/docs/scripts/generate.ts` — перед каждым `dev`/`build` пишет в
  `docs/generated/` (в `.gitignore`, не коммитится):
  - `packages-graph.md` — граф пакетов и приложений из `package.json` каждого `apps/*`/`packages/*`.
  - `modules-roadmap.md` — карта модулей из `ROADMAP.md` (появится в Фазе 11) и `docs/modules/*`.
  - `project-status.md` — открытые пункты `docs/BACKLOG.md`, список ADR, реестр переменных окружения (только имена и назначение, без значений — раздел 10.3 задания), покрытие тестами по пакетам (из `coverage/coverage-summary.json`, если он есть).
  - `api-reference.md` + `openapi.json` — список маршрутов, порождённый тем же `OPENAPIGenerator`/`ZodToJsonSchemaConverter`, что `GET /openapi.json` на сервере в разработке (раздел "Фаза 5" задания, пункт 5.1) — не переписаны руками.
- `vue` — прямая зависимость `apps/docs`, не только `vitepress`: содержимое читается из `docs/` вне `apps/docs`, и Rollup резолвит `vue`/`vue/server-renderer` от пути самого markdown-файла при сборке, а не от `node_modules` VitePress — pnpm 11 (strict) не отдаёт транзитивную зависимость в этом сценарии без явного объявления и Vite-алиаса в `config.ts` (найдено настоящей сборкой — без этого двух шагов она падает на "Rollup failed to resolve import vue/server-renderer").

## Как с этим работать

```bash
pnpm --filter docs-site dev      # генерация + локальный предпросмотр (http://localhost:5173)
pnpm --filter docs-site build    # генерация + статическая сборка в apps/docs/.vitepress/dist
pnpm --filter docs-site preview  # просмотр уже собранного dist
```

Добавить новую сгенерированную страницу: написать функцию в
`scripts/generate.ts`, вызвать её из `main()`, добавить ссылку в
`themeConfig.sidebar`/`nav` в `config.ts`. Страница, написанная руками
(обычный файл в `docs/`), появляется на сайте сама — достаточно
добавить её в `sidebar`, если она должна быть видна в навигации.

## Частые ошибки

- Редактировать файлы в `docs/generated/` руками — они перезаписываются
  при каждой сборке, правка пропадёт без следа.
- Забыть `.md` в ссылках внутри сгенерированных страниц — `pnpm check:docs`
  резолвит ссылки буквально по файлу на диске, расширение нужно даже
  там, где VitePress сам принимает оба варианта (`cleanUrls: true`).
- Запустить `vitepress build ../../docs` из `apps/docs` вместо
  `vitepress build .` — конфиг ищет `vitepress`/`vue` в `node_modules`
  того каталога, что передан CLI как root, не там, где физически лежит
  `.vitepress/`; `srcDir` в конфиге уже делает вывод содержимого из
  настоящего `docs/`, второй раз указывать путь к нему через CLI не нужно.

## Публикация

Сайт собирается в статические файлы (`apps/docs/.vitepress/dist`) и выкладывается на любой
статический хостинг. Задача `build-site` в `.github/workflows/docs.yml` собирает его и сохраняет
артефактом на каждый прогон; шаг публикации не добавлен, потому что он зависит от выбранного
хостинга (GitHub Pages, свой nginx, любой CDN) и его секретов.
