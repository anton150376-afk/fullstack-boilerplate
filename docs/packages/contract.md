> **Зачем читать:** как устроен контракт API и на что он опирается на
> сервере и в клиентах.
> **Кому:** кто добавляет или меняет маршрут API.
> **Последняя проверка:** 2026-10-11.

## Что это

Контракт API на **oRPC v1** (`@orpc/contract`) + **Zod 4** —
единственное место, где описаны входы, выходы, ошибки и HTTP-маршруты
API. Сервер (`apps/server`) реализует контракт через `@orpc/nest`; оба
будущих клиента (веб, мобильное — Фазы 6–7) будут читать его же через
`packages/api-client`. Типы выводятся из Zod-схем, рукописных дублей нет.

**Важно про версии** (D4, `ADR-0001-stack.md`): стабильная ветка oRPC —
v1 (`@orpc/*@1.15.5`), а сайт `orpc.dev` документирует уже v2-beta.
Примеры с сайта не переносятся буквально — ниже перечислены найденные
расхождения, установленные разбором типов самого пакета `node_modules`,
а не по памяти и не по сайту.

## Раскладка по доменам

Один файл `*.contract.ts` на домен в `src/`, запись в `src/index.ts`:
новый модуль добавляет файл и запись, существующие не трогает (раздел
"Фаза 5" задания, пункт 5.1). Домены — `notes` (показательная сущность
Фазы 4), `tasks` (сквозная проверка шаблона, Фаза 12.3: список, создание,
переключатель «сделано», удаление — `tasks.contract.ts`), `files` (талон
на загрузку, подтверждение) и `auditLog` (только чтение, Фаза 8 — запись
делают репозитории apps/server напрямую, не HTTP). Добавление `tasks`
потребовало ровно одного нового файла контракта и одной записи в
`src/index.ts`, существующие домены не менялись. **`health` сюда не входит**: это обычный REST
поверх `@nestjs/terminus` (`apps/server/src/health`), а не
бизнес-операция, и у него нет смысла в типизированных ошибках/
клиентской инвалидации кеша, которые даёт oRPC.

## Как выглядит процедура

```ts
import { oc } from "@orpc/contract";
import { z } from "zod";

export const notesContract = oc.tag("notes").router({
  get: oc
    .route({ method: "GET", path: "/notes/{id}", summary: "Одна заметка" })
    .input(z.object({ id: z.string() }))
    .output(noteSchema)
    .errors({
      NOT_FOUND: { status: 404, message: "Заметка не найдена", data: z.object({ id: z.string() }) },
    }),
});
```

- **Compact input-structure** (умолчание): поле `id` из `{id}` в пути
  сливается в один объект с остальным входом — для `GET` с query, для
  `POST`/`PATCH`/`DELETE` с телом. Отдельно `params`/`query`/`body`
  (`inputStructure: 'detailed'`) не нужны, пока вход не смешивает
  несовместимые по типу части запроса.
- `.meta({ widget: "textarea" })` на поле Zod-схемы — подсказка виду поля
  для конструктора админки (Фаза 8); тип поля сам по себе не говорит,
  однострочный это ввод или область текста.
- `.errors({ CODE: { status, message, data? } })` — коды берутся из
  общего набора (`BAD_REQUEST` 400, `NOT_FOUND` 404, …,
  `UNPROCESSABLE_CONTENT` 422, `INTERNAL_SERVER_ERROR` 500 — полный список
  в `node_modules/@orpc/client/dist/shared/client.*.mjs`,
  `COMMON_ORPC_ERROR_DEFS`); свой код допустим, но без описания в этом
  списке у него нет осмысленного дефолтного статуса/сообщения.

## Реализация на сервере: обязательные грабли

1. **Путь обязателен.** `@Implement` бросает исключение при старте, если
   у процедуры нет `path` в `.route()` — `populateContractRouterPaths` из
   `@orpc/contract` выводит путь из ключей роутера автоматически, но
   здесь не используется: явный путь читается в коде контракта без
   дополнительного разбора, что дороже при чтении, но дешевле при поиске.
2. **Сервис не знает про ORPCError.** `NotesService`/`FilesService`
   бросают обычные `NotFoundException`/`BadRequestException` — oRPC
   признаёт "определённой" только `ORPCError` с кодом из `.errors()`,
   иначе отдаёт непрозрачный 500. Перевод — один `try/catch` на границе
   каждого обработчика в контроллере (`notes.controller.ts`,
   `files.controller.ts`), не в сервисе: сервис остаётся пригодным для
   вызова не только из HTTP.
3. **`@Res() _res: Response` обязателен, даже неиспользуемый.**
   `ImplementInterceptor` сам пишет ответ напрямую в `res`
   (`StandardServerNode.sendStandardResponse`). Без параметра `@Res()` в
   сигнатуре метода Nest считает, что ответ не обработан
   (`isResponseHandled` в `@nestjs/core/router/router-execution-context.js`),
   и пытается отправить его повторно. Для обычных ответов второй вызов
   остаётся незамеченным, а для `successStatus: 204` (DELETE) роняет
   `Error: Cannot remove headers after they are sent to the client` —
   реальный клиент всё равно получает верный 204, но лог и процесс
   засоряются необработанным исключением. Найдено `test/notes.e2e-spec.ts`,
   воспроизведено и подтверждено исправлением (а не предположением).
4. **`@orpc/nest` ставится версией `latest` (`1.15.5`), не `beta`.**
   Страница интеграции с Nest на сайте показывает `npm install
@orpc/nest@beta` и использует `populateRouterContractOpenAPIPaths` —
   это v2 (`2.0.0-beta.x`, `pnpm view @orpc/nest dist-tags`). Стабильный
   путь — README самого установленного пакета
   (`node_modules/@orpc/nest/README.md`), а не страница на сайте.
5. **`@orpc/zod/zod4`, не `@orpc/zod`.** Корневой экспорт пакета читает
   типы из `zod/v3` (`import ... from 'zod/v3'` в его собственном
   `dist/index.d.mts`) и не распознаёт схемы Zod 4 — `ZodToJsonSchemaConverter`
   для генератора OpenAPI (`apps/server/src/openapi/`) берётся из
   подпути `@orpc/zod/zod4`.

## OpenAPI

`GET /openapi.json` (`apps/server/src/openapi/`) порождает спецификацию
из `contract` при каждом первом запросе (далее — из кеша в памяти
процесса) через `OpenAPIGenerator` + `ZodToJsonSchemaConverter`.
Маршрута нет вовсе при `NODE_ENV=production` (раздел "Фаза 5" задания,
пункт 5.1: "публикуется в разработке") — не скрыт, а отсутствует.

## Политика совместимости

Пока у API нет внешних потребителей (ни одного клиента вне этого
репозитория), ломающие изменения контракта разрешены без версионирования.
Версионирование вводится в момент появления первого потребителя, которого
нельзя поправить тем же коммитом — это может быть модуль аутентификации
(M1) или любой внешний интеграционный клиент. До этого момента ломающее
изменение просто требует правки сервера и обоих клиентов в том же
коммите — как и любое другое изменение контракта.

## Проверено механизмом: контракт без реализации ломает typecheck

Процедура, добавленная в `*.contract.ts` без соответствующего обработчика
в `implement(contract.<domain>)`, не доходит до рантайма — `tsc`
(`pnpm typecheck`, часть `pnpm gate`) требует, чтобы объект, возвращаемый
методом с `@Implement(contract.<domain>)`, содержал обработчик на каждый
ключ роутера контракта. Проверено намеренно: добавление лишней процедуры
в `notesContract` без обработчика в `NotesController` даёт
`Property '<имя>' is missing in type '{ list: ...; get: ...; }'` на шаге
`pnpm typecheck`; изменение отменено после проверки.

## Частые ошибки

- Проверять версии и примеры API по сайту `orpc.dev` вместо установленного
  `node_modules/@orpc/*` — сайт документирует v2-beta, а в проекте v1.
- Бросать `NotFoundException`/`BadRequestException` внутри
  `implement(...).handler(...)` напрямую — клиент получит 500 с чужим
  форматом ошибки вместо типизированной `ORPCError`.
- Забыть `@Res() _res: Response` в сигнатуре метода с `@Implement` на
  роутере — см. пункт 3 выше.
- Серверу в продакшене нужны скомпилированные файлы пакета: у каждой точки
  входа есть условие `compiled` → `dist/*.js` (скрипт `build`,
  `tsconfig.build.json`), сервер запускается как
  `node --conditions=compiled`. Поэтому `exports` содержит три ключа —
  `types`, `compiled`, `default`; не сводите их к одному
  (`docs/architecture/monorepo.md`, раздел «Условие compiled»;
  `pnpm check:runtime` проверяет это в гейте).
