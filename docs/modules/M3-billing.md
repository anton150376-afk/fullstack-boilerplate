## Назначение

Оркестратор платежей в API: продукт, план, цена, подписка, счёт,
платёж, право на функциональность по оплате, журнал событий. Ядро без
поставщиков (M3.1), затем российские поставщики — YooKassa (M3.2),
T-Bank (M3.3), покупки внутри приложений (M3.4), свой планировщик
подписок (M3.5). Полное описание и критериев приёмки —
[ROADMAP.md](../../ROADMAP.md#m3-биллинг).

## Границы

**Входит:** интерфейс адаптера поставщика (`createPayment`,
`chargeSavedMethod`, `parseWebhook`, `getPayment`/`refund`), таблица
прав на функциональность, журнал событий, тестовый адаптер, затем
реальные поставщики.

**Не входит:** Stripe/Paddle/Polar — недоступны как продавец-посредник
для российского юридического лица, это и определяет весь модуль
(российский поставщик реализуется первым).

## Точки интеграции

Пока ничего не заложено заранее — весь модуль появляется с M3.1.

Появится в этом модуле:

- `packages/contract` — публичный интерфейс адаптера.
- `apps/server` — оркестратор, обработчики webhook, таблица прав,
  планировщик продлений на BullMQ (поверх очередей из Фазы 4).
- `apps/mobile` — покупки внутри приложений (M3.4).

## Открытые вопросы

- RevenueCat или `expo-iap` без посредника для M3.4 — зависит от того,
  доступны ли выплаты Apple/Google на аккаунт разработчика (не
  решается кодом, проверяется до начала этапа).
- Статус `@jfkz/tinkoff-payment-sdk` (версия на дату задания — 2.0.2,
  апрель 2026) и `expo-iap`/`openiap` на дату начала M3.3/M3.4 —
  проверить заново, не по дате задания.
