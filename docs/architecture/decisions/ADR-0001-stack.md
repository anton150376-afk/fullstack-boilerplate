# ADR-0001: Стек коробочного решения

> **Статус:** принято (D1–D19), с отметками «требует подтверждения» там, где указано
> **Дата:** 2026-10-08

## Контекст

`docs/architecture/original-task.md` фиксирует решения D1–D19 как принятые и не подлежащие
пересмотру без явного указания, но требует, чтобы агент проверил их техническую
исполнимость на версиях, актуальных на дату выполнения, и оставляет агенту
четыре дополнительных решения. Проверка выполнена 2026-10-08: реестр npm,
Docker Hub, GitHub issues и официальная документация библиотек. Полная таблица
версий — `docs/architecture/versions.md`.

## Четыре решения, оставленные агенту разделом 3

| Вопрос                                                              | Решение                                                                                        | Обоснование                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сборка образов: `turbo prune` vs `pnpm deploy`                      | **`turbo prune` на первом этапе**, `pnpm deploy` не исключается для отдельных приложений позже | `turbo prune` — штатный путь в документации Turborepo для монорепозиториев именно этой формы (несколько `apps/*`, общие `packages/*`); не требует дополнительной настройки на пакет. `pnpm deploy` даёт более тонкий контроль, но требует отдельной настройки на каждое приложение — отложить до появления конкретной потребности (например, минимизации размера образа воркера). Статус: **требует подтверждения** на практике в Фазе 4                                                                                          |
| Движок DOM-тестов: `happy-dom` vs `jsdom`                           | **`jsdom`**                                                                                    | `@testing-library/react` и Base UI (всплывающие слои, фокус-менеджмент) ориентированы на поведение, максимально близкое к реальному браузеру; `jsdom` реализует больше DOM-API корректно (в частности, связанных с фокусом и диалогами), что для `ui-web` важнее скорости. `happy-dom` быстрее, но для тестов, где важны настоящие фокус и слои, задание само требует браузерный режим Vitest с Playwright — то есть `happy-dom`/`jsdom` закрывают только обычные компонентные тесты, где корректность важнее выигрыша в скорости |
| Персистентность кеша запросов в мобильном приложении                | **Не персистировать в Фазе 7**; оставить точку расширения                                      | Персистентный кеш TanStack Query в React Native обычно означает `AsyncStorage` или MMKV в качестве синхронного персистера — лишняя зависимость и риск до того, как понятен реальный профиль офлайн-использования приложения. Задание уже требует никогда не персистировать кеш аутентификации; остальное — пункт `docs/BACKLOG.md` с пометкой «риск», решается ADR отдельно при первой реальной потребности в офлайн-режиме                                                                                                       |
| Образ S3-совместимого хранилища для разработки: Garage vs SeaweedFS | **Garage**, как и предполагало задание                                                         | Прямое указание задания (D16) — не MinIO. Между Garage и SeaweedFS выбор в пользу Garage: меньше площадь поверхности (однородный бинарник, меньше режимов работы), встроенная модель `forcePathStyle`-совместимого доступа «из коробки» для одного узла разработки. SeaweedFS интереснее для многоуровневого хранения (несколько классов дисков) — это не нужно в compose для разработки. Версия образа пересмотрена с `v1.0.1` на фактический актуальный релиз **v2.4.1** (см. таблицу выше)                                     |

## Последствия

- Версии, зафиксированные здесь и в `docs/architecture/versions.md`, попадают
  в `catalog:` `pnpm-workspace.yaml` в Фазе 1 без повторного обоснования.
- Три расхождения с заданием (`@nestjs/bullmq` 12 vs 11.0.5, Garage `v2.4.1`
  vs `v1.0.1`, Vite 8 статус) перенесены в `docs/BACKLOG.md` как пункты,
  которые нужно закрыть точечной проверкой перед соответствующей фазой
  (4, 4, 6).
- `nestjs-pino` и TypeScript 6 vs 7 — неопределённости задания сняты
  исследованием, обратного пересмотра не требуется.
