## 0. Как запускать это задание

Задание разбито на 13 фаз (0–12). У каждой есть цель, список работ, критерии приёмки,
проверяемые командами, и список того, что нужно записать в документацию.

Порядок работы с Claude Code:

1. Создать пустой репозиторий, положить этот файл в корень как `BOILERPLATE_TASK.md`.
2. Выполнять **по одной фазе за сессию**:
   `Прочитай BOILERPLATE_TASK.md и выполни Фазу 0. Остальные фазы не трогай.`
3. Фаза 0 заканчивается таблицей версий и решениями — их нужно просмотреть глазами.
4. После каждой фазы: `pnpm verify`, коммит, `/clear`, следующая фаза.
   Фазы 3, 4 и 8 в одну сессию не влезут — у них внутри указаны точки,
   где сессию можно закончить чисто.
5. Начиная с Фазы 3 в репозитории работает собственная обвязка (`AGENTS.md`,
   `.claude/rules`, скиллы, блокирующий гейт). Дальше агент опирается на неё,
   а этот файл остаётся сверочным листом.

Фазы 0–3 закладывают правила, по которым пишется весь остальной код, поэтому их порядок
менять нельзя. Фазы 4–9 можно вести разными сессиями, если каждая заканчивается
зелёным `pnpm verify`.

**Требование к инструменту:** Claude Code версии 2.1.277 или новее — на более старых
`AGENTS.md` не читается автоматически, и обвязка из Фазы 3 работать не будет.

## 1. Что строим

Монорепозиторий-основа, из которого разворачиваются продуктовые проекты: API, веб,
мобильное приложение, общие пакеты конфигураций и кода, общая система тестов,
живая документация и обвязка для работы агентов.

Три свойства, ради которых всё это делается:

**Один фундамент для двух интерфейсов.** Веб и мобильное приложение используют один
контракт API, одну клиентскую фабрику запросов, одну палитру и парные компоненты
с одинаковыми именами и пропсами. Изменения переносятся между ними механически.

**Механизм согласованности, который нельзя обойти.** Код не считается написанным, пока
он не покрыт тестами, не прошёл линтер, не описан в документации и пока остаток работ
не зафиксирован. Держится это на блокирующем гейте, а не на напоминаниях (раздел 13).

**Заготовленные места для будущих модулей.** Аутентификация, права, биллинг и
уведомления появятся позже, этапами, по единой процедуре (раздел 15).

## 2. Роль агента и принципы работы

**Роль:** инженер, который собирает фундамент для долгоживущих проектов. Решения
принимаются с оглядкой на то, что через полгода их будет читать другой человек
и другой агент.

### 2.1 Принципы

1. **Проверяй, не вспоминай.** Версии, имена API и флаги CLI берутся из реестра и
   актуальной документации на дату выполнения. Таблица в разделе 4 — отправная точка,
   а не истина: её нужно перепроверить.
2. **Маленькие проверяемые шаги.** Каждый шаг заканчивается командой, показывающей
   результат.
3. **Решение без следа не существует.** Любой выбор с альтернативами — в ADR
   (`docs/architecture/decisions/`).
4. **Честный остаток.** Всё недоделанное и обойдённое попадает в `docs/BACKLOG.md`
   в том же коммите, где возникло.
5. **Документация в том же коммите, что и код.** Отложенная документация не пишется.

### 2.2 Жёсткие запреты

- Хардкодить версии «по памяти». Версии ставятся менеджером пакетов и фиксируются
  lock-файлом; общие версии живут в каталоге рабочей области.
- `any`, `@ts-ignore`, `eslint-disable` без комментария с причиной и ссылкой на
  правило или на пункт бэклога.
- Коммитить секреты. Ключи только через `.env`, в репозитории лишь `.env.example`.
- Пропускать или отключать падающие тесты, чтобы пройти дальше.
- `git push --force`, `rm -rf` вне рабочего каталога, правка lock-файла руками.
- Нейрослоп в документации (раздел 14).
- Расширять объём. Модули из ROADMAP в Фазах 0–12 **не реализуются**: готовятся
  только места интеграции и описания этапов.

### 2.3 Когда останавливаться и спрашивать

Агент решает сам по правилу: проверить документацию → сравнить варианты по критериям
→ выбрать → записать ADR. Остановиться нужно, если требуется платный аккаунт или
внешний сервис с биллингом; если выбор меняет публичный контракт уже написанного кода
других фаз; если требование этого файла противоречит само себе или невыполнимо на
текущих версиях библиотек. В последнем случае противоречие сначала записывается
в бэклог.

Если спросить некого, выбрать вариант с наименьшим числом необратимых последствий,
пометить ADR статусом `требует подтверждения` и продолжить.

## 5. Грабли, собранные заранее

Список реальных ловушек, найденных в документации. Прочитать до начала работы;
каждая из них стоит часов отладки.

1. **Metro и `exports`.** Metro не подставляет расширения для путей из `exports`,
   поэтому внутренние пакеты обязаны указывать **полный путь к файлу**:
   `"./index": "./src/index.ts"`. Запись без расширения не разрешится. Условие
   `"react-native"` ставится **выше** `import`, `require` и `default`;
   для веб-сборки `"browser"` идёт выше `"react-native"`.
2. **Metro и TS-пути.** `paths` из `tsconfig.json` Metro не читает. Межпакетные
   импорты только через имена пакетов.
3. **Expo и монорепозиторий.** С SDK 52 Metro настраивается автоматически.
   Документация велит **удалить** `watchFolders`, `resolver.nodeModulesPath`,
   `resolver.extraNodeModules` и `resolver.disableHierarchicalLookup`, если они есть.
   Писать их заново — ошибка. `node-linker=hoisted` тоже больше не нужен.
4. **Дубликаты `react` и `react-native`.** Две версии в дереве — гарантированная
   поломка сборки. Проверять `pnpm why --depth=10`, при необходимости фиксировать
   через `overrides` в корне.
5. **Uniwind и `@source`.** Tailwind 4 сканирует от каталога с CSS-входом и **не ходит
   по симлинкам pnpm**. Классы из `packages/ui-native` и `packages/ui-core` невидимы,
   пока не перечислены директивами `@source` с путями **относительно CSS-файла**.
   Указывать нужно на исходники, а не на `dist`; после правки — перезапуск Metro.
6. **Uniwind и Metro.** `withUniwindConfig` должен быть самой внешней обёрткой.
   `cssEntryFile` задаётся строкой с путём от корня проекта; `path.resolve` отвергается.
   CSS импортируется в корневом компоненте (`app/_layout.tsx`), а не в точке
   регистрации — иначе ломается горячая перезагрузка.
7. **Uniwind на бесплатной ветке.** `hover:` и `group-*` не действуют. В общих
   примитивах их не использовать.
8. **`oklch` на мобильном.** Uniwind значения понимает, но `react-native-svg`
   и сырые RN-стили — нет. Держать hex-зеркало палитры для таких потребителей.
9. **TanStack Query: устаревшие API.** `ensureQueryData`, `fetchQuery` и
   `prefetchQuery` объявлены устаревшими; замена — `queryClient.query(opts)`,
   а поведение `ensureQueryData` воспроизводится как
   `queryClient.query({ ...opts, staleTime: 'static' })`.
10. **TanStack Start: `routerWithQueryClient` исчез.** Актуальное —
    `setupRouterSsrQueryIntegration` из `@tanstack/react-router-ssr-query`.
    Руками делать `dehydrate`/`hydrate` вместе с интеграцией нельзя.
11. **Документация Start отстаёт.** Страница обзора называет проект Release Candidate,
    страница хостинга показывает мёртвый `app.config.ts`. Ориентироваться на
    `vite.config.ts` и на опубликованные версии 1.x.
12. **Vitest 5: конфиги не ищутся вверх по дереву.** Пакет без своего конфига
    просто не тестируется, без ошибки. Глобы в `projects` задавать явно и проверять
    число проектов в CI.
13. **Vitest 5: покрытие только в корне.** Пороги на отдельный проект не
    поддерживаются; нужны пороги по шаблонам путей в корневом конфиге.
14. **Vitest 5: моки чистятся перед каждым тестом.** Наборы, опирающиеся на
    сохранение состояния `vi.fn()` между тестами, тихо сломаются.
15. **pnpm 11: `onlyBuiltDependencies` удалён.** Замена — `allowBuilds`. Конфиг,
    перенесённый из шаблонов эпохи pnpm 10, молча не работает.
16. **pnpm 11: `.npmrc` только для реестра и авторизации.** Остальное переехало
    в `pnpm-workspace.yaml`; поле `pnpm` в `package.json` игнорируется.
17. **pnpm 11: `minimumReleaseAge` по умолчанию сутки.** Свежие релизы выглядят
    отсутствующими. Это ожидаемо, записать в документацию.
18. **`erasableSyntaxOnly` и Nest.** Флаг запрещает параметры-свойства конструктора,
    на которых держится внедрение зависимостей. В серверной апке не включать.
19. **Prettier и Tailwind 4.** Плагину нужен `tailwindStylesheet`, и один корневой
    конфиг не описывает два CSS-входа. Решение — свой `.prettierrc` в каждой апке,
    общие опции из пакета. Вариант с `overrides` не документирован, не использовать.
20. **`turbo --affected` и неполный клон.** При shallow clone определение изменений
    молча деградирует до «собрать всё». В CI нужен `fetch-depth: 0`.
21. **Turbo и переменные окружения.** Необъявленные в `env`/`globalEnv` переменные
    дают ложные попадания в кеш. Объявлять все, что влияют на сборку.
22. **terminus 12.** Базовый класс `HealthIndicator` и `getStatus()` удалены;
    используется `HealthIndicatorService`. Готового индикатора для Redis нет.
    Исключение внутри индикатора даёт 500, а возврат `down` — 503.
23. **BullMQ Job Schedulers.** Опция `utc` удалена (теперь `tz: 'UTC'`), свой
    `jobId` задать нельзя, а следующий запуск создаётся в момент начала обработки
    предыдущего — на загруженной очереди интервал фактически растягивается.
24. **shadcn в монорепозитории.** Каждой рабочей области нужен свой
    `components.json`; значения `style`, `iconLibrary` и `baseColor` обязаны
    совпадать. Есть открытые ошибки с неверным размещением файлов, поэтому
    коммит перед каждым `add`. Утилита `cn` переехала в отдельный пакет.
25. **`.mcp.json` в CI.** В неинтерактивных запусках серверы MCP подключаются
    **без запроса подтверждения**. Держать файл минимальным.
26. **В Hermes нет `Intl.PluralRules`.** На RN 0.86 и Expo SDK 57 доступны
    `Intl.NumberFormat`, `Intl.DateTimeFormat` и `Intl.Collator`, а
    `PluralRules`, `RelativeTimeFormat`, `ListFormat` и `Locale` отсутствуют.
    Без них русские множественные формы посчитать нельзя. Хуже того, i18next
    начиная с версии 24 **не имеет внутреннего запасного механизма**: без
    полифила разрешаются только английские `_one` и `_other`, и приложение
    молча показывает неправильную грамматику вместо того, чтобы упасть.
    Полифилы `@formatjs/intl-locale` и `@formatjs/intl-pluralrules`
    импортируются из точек входа `/polyfill-force` в корне приложения
    **до** инициализации локализации.
27. **Русские множественные формы — четыре ключа, не два.** `_one` (1, 21, 31),
    `_few` (2–4, 22–24), `_many` (0, 5–20, 25–30), `_other` (только дробные).
    Переменная обязана называться `count`. Проверка в гейте: для каждого ключа
    с `_one` в русском каталоге существуют `_few` и `_many`.
28. **MinIO больше не поддерживается.** Репозиторий заархивирован в апреле
    2026 с явной пометкой об этом; до того из бесплатной редакции убрали
    консоль администрирования, а затем прекратили сборку бинарников и образов.
    В compose его не ставить. Для разработки — Garage (`dxflrs/garage`) либо
    SeaweedFS; оба требуют `forcePathStyle: true` и не поддерживают
    блокировку объектов и версионирование.
29. **AWS SDK ломает совместимость с не-AWS хранилищами.** Начиная с версии
    3.729.0 клиент отправляет контрольные суммы CRC32 на всех запросах PUT
    и проверяет их на GET, из-за чего отказывают R2, Backblaze, Spaces и
    S3-совместимые серверы. Обязательно задать
    `requestChecksumCalculation: "WHEN_REQUIRED"` и
    `responseChecksumValidation: "WHEN_REQUIRED"`, зафиксировать версию SDK
    и добавить интеграционный тест против поднятого в compose хранилища:
    модульные тесты такую регрессию не ловят.
30. **Подписанный PUT не ограничивает размер загрузки.** Это распространённая
    дыра: в подписанной ссылке размер можно ограничить только подписав заголовок
    `Content-Length`, который клиент просто не отправляет. Использовать
    **подписанную форму POST**: политика входит в подпись, и хранилище само
    отвергает запрос при нарушении `content-length-range` или типа содержимого.
    Все поля формы, кроме подписи, самого файла, политики и полей `x-ignore-*`,
    обязаны быть перечислены в условиях. Настоящий тип всё равно проверять
    по сигнатуре файла на стороне сервера после загрузки.
31. **TanStack Table v9 сменила API.** `useReactTable` стал `useTable`,
    состояние переехало на TanStack Store, возможности подключаются по выбору.
    Готовые примеры таблиц shadcn для v9 на момент проверки ещё не догнали,
    а управляемое состояние через новые атомы не является прямой заменой
    прежнего — рассчитывать на свой компонент.
32. **`validateSearch` принимает Zod 4 напрямую.** Адаптер `zodValidator`
    нужен только для Zod 3; добавлять его поверх Zod 4 излишне.
33. **Админка выпадает из проверки паритета.** `packages/admin-kit` —
    веб-только, его нужно внести в исключения `check-parity`, иначе проверка
    потребует несуществующей мобильной пары.
34. **Старый API загрузки файлов в Expo объявлен устаревшим.** Использовать
    новый классовый API `expo-file-system`; не собирать псевдо-Blob из
    `{ uri, type, name }` и не читать файлы в base64 — это утраивает расход
    памяти и падает на крупных медиафайлах.

## 7. Параллельная работа нескольких человек

Решение рассчитано на то, что над проектом работают несколько человек, и у каждого
может быть своя сессия агента. Это накладывает требования, которые дешевле заложить
сразу, чем вводить после первого болезненного слияния.

### 7.1 Что можно вести параллельно, а что требует согласования

| Область                             | Режим                                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------- |
| Разные пакеты и приложения          | **Параллельно.** Границы импортов и проверка `turbo boundaries` не дают работам пересечься  |
| `packages/contract`                 | **По согласованию.** Домены разложены по файлам, но два человека в одном домене конфликтуют |
| Схема Prisma и миграции             | **По одному.** См. 7.3 — самое узкое место                                                  |
| Токены `packages/tailwind-config`   | **По согласованию.** Правка палитры задевает оба интерфейса                                 |
| Каталоги локализации                | **Параллельно при раскладке по доменам.** См. 7.5                                           |
| `pnpm-lock.yaml` и каталог версий   | **По одному.** См. 7.4                                                                      |
| `.claude/rules`, `turbo.json`, гейт | **По согласованию через pull request.** Это общие правила, меняющие поведение у всех        |
| `docs/BACKLOG.md`                   | **Параллельно** при схеме идентификаторов из 7.6                                            |

Таблицу держать в `CONTRIBUTING.md` и обновлять при появлении новых общих мест.

### 7.2 Ветки, ревью, защита `main`

- Ветки `feat/*`, `fix/*`, `chore/*` от `main`; прямые пуши в `main` закрыты.
- Обязательные проверки для слияния — задача гейта из CI. Без неё слияние
  невозможно, и это главная причина, по которой гейт должен быть быстрым.
- Один pull request — одна связная работа. Ревью одного человека, кроме автора.
  При работе в одиночку роль ревью выполняет подагент `reviewer` в свежем
  контексте: он не видел, как писался код, и потому замечает больше.
- `CODEOWNERS` по пакетам, чтобы запрос на ревью уходил тому, кто за область отвечает.
- Слияние со сжатием в один коммит либо линейная история — выбрать одно
  и записать в `CONTRIBUTING.md`.

### 7.3 Миграции базы данных

Самое вероятное место конфликта: две ветки добавляют по миграции, порядок применения
на разных машинах расходится, журнал применённых миграций конфликтует. Процедура:

1. Перед генерацией миграции подтянуть `main` и перебазироваться.
2. Одна миграция на pull request. Несколько изменений схемы в одной работе
   собираются в одну миграцию.
3. **Применённую миграцию не править никогда.** Исправление — это новая миграция.
4. Если во время ревью в `main` попала чужая миграция, автор перебазируется,
   удаляет свою, генерирует заново и проверяет результат на чистой базе.
5. Удаление и переналивка локальной базы — штатная операция, под неё есть скрипт
   и детерминированные сиды.

Проверка в CI: состояние миграций и соответствие схемы применённым миграциям.
Расхождение роняет сборку. Это ловит и забытую генерацию, и правку применённой
миграции.

### 7.4 Lock-файл и каталог версий

- `pnpm-lock.yaml` руками не сливается никогда. При конфликте взять версию из
  базовой ветки, повторить установку, закоммитить результат.
- Запись в lock-файл агенту запрещена разрешениями, но процедура нужна человеку.
- Изменение каталога версий (`catalog:`) — отдельный pull request, не попутно
  с функциональной работой: он задевает все пакеты сразу.

### 7.5 Каталоги локализации

Один большой JSON на язык порождает конфликты, которые неприятно разрешать.
Поэтому: каталоги раскладываются по доменам (по файлу на область), ключи
сортируются детерминированно, и сортировка проверяется `check-i18n`. Тогда
конфликты становятся построчными и разрешаются механически.

### 7.6 Бэклог без коллизий

Последовательная нумерация вида `B-001` при параллельной работе гарантированно даёт
двух авторов с одним номером. Схема идентификатора: **`B-<ГГММДД>-<короткий-слаг>`**,
например `B-261008-redis-tests`. Дата делает его уникальным и сортируемым,
слаг — читаемым.

В таблицу добавляется колонка **владельца**. Правило, проверяемое `check-backlog`:
пункт в статусе «В работе» без владельца роняет гейт. Пункт в статусе «Открыто»
владельца не требует.

Когда людей станет больше трёх, бэклог в markdown перестанет справляться — тогда
он переезжает в issues на GitHub, а `check-backlog` начинает читать их через `gh`.
Это отдельный пункт ROADMAP, заранее его не делать.

### 7.7 Общий кеш сборки

Без общего кеша второй человек платит полным временем сборки и тестов. Удалённый
кеш Turborepo это снимает: у Vercel он бесплатен независимо от того, где
развёрнуты приложения, либо поднимается свой на любом хосте с S3-совместимым
хранилищем. Решение и выбор — в ADR, с двумя оговорками в документации:
содержимое кеша покидает машину, поэтому для закрытого проекта предпочтителен
свой; и корректность кеша целиком зависит от полноты объявленных
переменных окружения (см. грабли).

### 7.8 Два агента на одной машине

Каждой задаче — свой git worktree. Две сессии в одном рабочем дереве затирают
друг другу правки, и это обнаруживается не сразу. Claude Code умеет работать
в изолированном worktree; как это запускать — описать в `CONTRIBUTING.md`.

### 7.9 Разделение локальных сред

Два человека одновременно — это два набора контейнеров. Задать свой
`COMPOSE_PROJECT_NAME` на разработчика либо развести порты через
`docker-compose.override.yml`, который в репозиторий не попадает. Образец —
в `docker-compose.override.yml.example`.

### 7.10 Общий `.claude/`

Каталог коммитится, то есть правка правила меняет поведение агента у всех. Это
и задумано, но следствие нужно принять: изменения в `.claude/` проходят ревью
как код. Личные настройки — только в `settings.local.json`, который в `.gitignore`.

### 7.11 Онбординг нового человека

Страница `docs/guides/onboarding.md`, отдельная от `getting-started.md`
(та отвечает за путь от клона до запуска):

- что должно быть установлено и какие версии;
- какие аккаунты нужны (реестр пакетов, EAS для сборок, хранилище, реестр образов);
- **как передаются секреты**: менеджер паролей, не переписка и не файл в репозитории.
  `.env.example` — это контракт, а не источник значений;
- как получить development build на своё устройство;
- первая задача: взять пункт из бэклога, провести по циклу `feature-workflow`,
  довести до зелёного гейта.

## Фаза 0. Разведка и решения

**Цель:** зафиксировать версии и подтвердить решения до первой строки кода.

### Работы

1. Проверить окружение: Node ≥22, pnpm 11 через corepack, доступность Docker.
2. Пройти таблицу раздела 4 и получить актуальную версию каждого пакета из реестра.
   Расхождения с таблицей — повод обновить таблицу, а не игнорировать.
3. Проверить по документации связки, которые ломаются чаще всего. Минимум:
   - oRPC: имена `@orpc/nest` (`@Implement`, `ORPCModule.forRoot`) и
     `createTanstackQueryUtils` из `@orpc/tanstack-query`; требования к версии Nest;
     что именно отличается между стабильной v1 и документацией v2.
   - TanStack: `setupRouterSsrQueryIntegration`, `queryClient.query`, минимальная
     версия Query.
   - Prisma: `prismaSchemaFolder`, порядок генерации клиента в монорепозитории.
   - terminus 12: `HealthIndicatorService`, `withTimeout`, `cacheFor`.
   - Uniwind: `withUniwindConfig`, `cssEntryFile`, `@source`, список
     неподдерживаемых утилит.
   - Vitest 5: `test.projects`, `defineProject`, пороги покрытия по шаблонам.
   - Hermes: какие конструкторы `Intl` есть на текущей версии RN, а какие
     требуют полифила. Это проверить **фактически**, а не по статье: от ответа
     зависит правильность русской грамматики.
   - AWS SDK: действует ли ещё отправка контрольных сумм по умолчанию и те ли
     имена у настроек её отключения.
   - Состояние образов S3-совместимых хранилищ для разработки (Garage,
     SeaweedFS): текущие теги, порты, лицензии.
   - TanStack Table v9: имена `useTable` и `useLegacyTable`, работа
     с управляемым состоянием; появились ли примеры таблиц shadcn для v9.
4. Создать минимум документации, нужный уже сейчас: `docs/architecture/decisions/`
   с шаблоном ADR, `docs/architecture/versions.md`, `docs/README.md` с заготовкой
   карты, `docs/BACKLOG.md` с пустыми разделами.
5. Оформить `ADR-0001-stack.md`: подтверждение решений D1–D19 с датой и ссылками,
   плюс четыре решения, оставленных агенту (раздел 3).
6. Записать в `docs/BACKLOG.md` всё, что выглядит рискованным: расхождения версий,
   неподтверждённые утверждения, места, где документация противоречит релизам.

### Критерии приёмки

- `docs/architecture/versions.md` содержит таблицу «пакет → версия → дата → источник».
- `ADR-0001-stack.md` подтверждает или оспаривает каждое решение D1–D19.
- Ни одна версия нигде не указана без источника.

   настройки pnpm, кроме реестра и авторизации:
   - `catalog:` для версий, которые должны совпадать всюду — react, typescript,
     zod, пакеты tanstack, tailwindcss, vitest, пакеты orpc. Каталог — единственное
     место, где версия записана текстом.
   - `catalogMode: strict` после первого прохода, `catalogPrune: true`.
   - `linkWorkspacePackages: false` и явные `workspace:*` в зависимостях: так
     отсутствующий пакет падает громко, вместо тихой загрузки из реестра.
   - `allowBuilds` с явным перечислением пакетов, которым нужен postinstall.
   - `nodeLinker` оставить по умолчанию (isolated): Expo поддерживает симлинки pnpm
     с SDK 54.
3. **`.npmrc`** только для реестра и авторизации.
4. **`turbo.json`.** Ключ `tasks`, задачи `build`, `lint`, `typecheck`, `test`,
   `test:coverage`, `dev`, `check:*`. У каждой объявлены `inputs`, `outputs`,
   `dependsOn`. Задача `dev` — `persistent: true`, без кеша. Все переменные
   окружения, влияющие на сборку, перечислены в `env`/`globalEnv`. `futureFlags`
   не включать.
5. **`packages/typescript-config`.** `base.json`: `strict`,
   `noUncheckedIndexedAccess`, `verbatimModuleSyntax`. Флаг
   `exactOptionalPropertyTypes` оставить выключенным. Варианты:
   - `node.json` — `moduleResolution: "nodenext"`, **без** `erasableSyntaxOnly`
     (ломает параметры-свойства конструктора в Nest);
   - `react.json` и `react-native.json` — `moduleResolution: "bundler"`,
     `erasableSyntaxOnly` можно включить;
   - `package.json` для пакетов, собираемых `tsc`.
6. **Корневой `vitest.config.ts`.** Проекты через `test.projects` с явными глобами;
   покрытие настраивается **только здесь** (провайдер `v8`, пороги по шаблонам
   путей). Запомнить: конфиги не ищутся вверх по дереву, поэтому у каждого
   тестируемого пакета должен быть свой `vitest.config.ts` с `defineProject`.
7. **Служебные файлы.** `.gitignore` (включая `.claude/settings.local.json`,
   `.bugs/`, `.env`), `.gitattributes`, `.editorconfig`, `.dockerignore`.
8. `git init`, первый коммит.

### Скрипты корня

```jsonc
{
  "dev": "turbo run dev",
  "build": "turbo run build",
  "lint": "turbo run lint",
  "lint:fix": "turbo run lint -- --fix",
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "typecheck": "turbo run typecheck",
  "typecheck:fast": "tsgo --noEmit -p tsconfig.json",
  "test": "vitest run",
  "test:watch": "vitest",
  "test:coverage": "vitest run --coverage",
  "test:mobile": "pnpm --filter mobile test",
  "check:docs": "tsx scripts/check-docs.ts",
  "check:backlog": "tsx scripts/check-backlog.ts",
  "check:parity": "tsx scripts/check-parity.ts",
  "check:i18n": "tsx scripts/check-i18n.ts",

  "docker:up": "docker compose up -d",

```

`pnpm verify` и `pnpm gate` — одна и та же проверка. Она стоит в CI и в блокирующем
хуке завершения сессии. Скрипт `typecheck:fast` на `tsgo` необязателен и в гейт
не входит: он нужен для быстрой локальной проверки типов, пока `typescript-eslint`
не поддерживает TypeScript 7.

### Критерии приёмки

- `pnpm install` проходит; оставшиеся предупреждения о peer-зависимостях
  объяснены в `docs/BACKLOG.md`.
- `pnpm verify` проходит на пустом каркасе.
- `pnpm turbo run build --dry-run=json` показывает ожидаемый граф.
- Повторный `pnpm lint` берётся из кеша (`FULL TURBO`).

## Фаза 2. Общие пакеты конфигураций

**Цель:** одно место для правил кода и одно место для палитры.

### Работы

1. **`packages/prettier-config`.** Общий объект настроек плюс сортировка импортов.
   Плагин `prettier-plugin-tailwindcss` подключается **в каждой апке отдельно**:
   у `apps/web` и `apps/mobile` свой `prettier.config.mjs`, который разворачивает
   общий конфиг и задаёт собственный `tailwindStylesheet`. Один корневой конфиг
   два CSS-входа описать не может.
2. **`packages/eslint-config`.** Flat config, экспорты `base`, `node`, `react`,
   `native`, `test`:
   - `base` — `typescript-eslint` с `strictTypeChecked` и
     `parserOptions.projectService: true` (именно это заставляет типизированный
     линтинг работать в монорепозитории без перечисления всех tsconfig);
   - `react` — hooks, `jsx-a11y`, `@tanstack/eslint-plugin-query`;
   - `native` — поверх `react`, плюс правила React Native;
   - границы импортов через `no-restricted-imports`: приложение не импортирует
     другое приложение, импорт пакета только через публичную точку входа,
     прямые обращения к сети вне `packages/api-client` запрещены;
   - кеш линтера включён и объявлен как `outputs` в turbo.
     Дополнительно включить `turbo boundaries` как отдельную задачу CI: она ловит
     импорты необъявленных зависимостей, чего линтер не видит. Функция
     экспериментальная, поэтому падение этой задачи разбирается, а не игнорируется.
3. **`packages/tailwind-config`.** Tailwind ≥4.3.3, конфигурация через CSS:
   - `src/theme.css` — `@theme` с токенами: палитра (brand, accent, neutral,
     success, warning, danger по шкале 50–950), радиусы, типографика, отступы,
     тени; значения в `oklch`;
   - семантические переменные для светлой и тёмной тем ссылаются на шкалу палитры;
   - `src/base.css` — сброс и базовые слои для DOM;
   - `src/tokens.ts` — **hex-зеркало палитры** для потребителей, которые не умеют
     `oklch`: `react-native-svg`, сырые стили RN, генераторы иконок. Зеркало
     порождается скриптом из `theme.css`, чтобы значения не расходились,
     и проверяется тестом;
   - `exports`: `./theme.css`, `./base.css`, `./tokens`.
4. **`packages/i18n`.** Локализация для веба, мобильного и сервера из одного места.
   - `i18next` с плоскими каталогами JSON: ни шага сборки, ни макросов, поэтому
     один пакет одинаково работает под Vite, под Metro и на сервере для писем
     и текстов ошибок.
   - Языки `ru` и `en` с первого дня. Русские формы множественного числа —
     **четыре ключа** (`_one`, `_few`, `_many`, `_other`), переменная называется
     `count`.
   - Экспорты: каталоги, инициализатор, типы ключей, обёртки форматирования
     даты, числа и относительного времени.
   - Полифилы `Intl` **не импортируются здесь**: они нужны только мобильному
     приложению и подключаются в его точке входа (Фаза 7), чтобы не тащить вес
     в веб.
   - Проверка в гейте: `scripts/check-i18n.ts` — наборы ключей в языках
     совпадают; у каждого ключа с `_one` в русском каталоге есть `_few`
     и `_many`; нет неиспользуемых и отсутствующих ключей.
5. **`packages/testing`.** Пресеты Vitest (node, dom), setup-файлы, фабрики тестовых
   данных, утилиты подмены сети, матчеры. Пресеты для React Native сюда не идут:
   мобильное приложение тестируется Jest и держит свою настройку у себя.
6. Для каждого пакета — короткий `README.md` и страница в `docs/packages/`.

### Критерии приёмки

- Любой пакет подключает линтер тремя строками и получает одинаковые правила.
- Значения цветов не дублируются: семантические переменные ссылаются на палитру,
  а hex-зеркало порождается из `theme.css` и сверяется тестом.
- Есть `docs/guides/styling.md` с описанием, как добавить токен и как он доезжает
  до веба и до мобильного.
- Есть `docs/guides/i18n.md`: как добавить строку, как устроены русские формы
  множественного числа, почему мобильному нужны полифилы.
- `pnpm check:i18n` падает, если в русском каталоге у ключа с `_one`
  отсутствуют `_few` и `_many` (проверить намеренным нарушением).
- `pnpm verify` зелёный.

## Фаза 3. Обвязка агентов и система документации

**Цель:** включить механизм согласованности до появления прикладного кода.
Эта фаза определяет, как пишется весь дальнейший код.

### 3.1 Как устроена обвязка

Четыре уровня, от постоянного к ситуативному:

```text
AGENTS.md              всегда в контексте: что за репозиторий, карта, контракт работы
  CLAUDE.md            одна строка @AGENTS.md — для совместимости
.claude/rules/*.md     подгружаются только при работе с файлами из их paths
.claude/skills/*       процедуры, подгружаются при вызове
docs/*                 объяснения для человека
```

Принцип, на котором держится конструкция: **документ не повторяет содержимое другого
документа, он на него ссылается**. Разросшийся файл инструкций перестаёт
исполняться, поэтому `AGENTS.md` держится в пределах 150 строк, а подробности
уходят в правила и скиллы.

### 3.2 `AGENTS.md` и `CLAUDE.md`

Claude Code читает `AGENTS.md` сам, но при наличии обоих файлов читает **только**
`CLAUDE.md`. Поэтому:

- `AGENTS.md` — единственный содержательный файл, до 150 строк;
- `CLAUDE.md` — ровно одна строка `@AGENTS.md`.

Состав `AGENTS.md`:

1. Что за репозиторий и из чего состоит, со ссылкой на `docs/architecture/overview.md`.
2. **Контракт работы, пять строк:** перед правкой кода прочитать правила, которые
   подгрузятся сами; работа завершается только после прохождения `pnpm gate`;
   недоделки идут в `docs/BACKLOG.md`; документация правится в том же коммите;
   решения с альтернативами оформляются ADR.
3. Карта репозитория: таблица «каталог → назначение → где документация».
4. Команды на каждый день.
5. Что делать при неопределённости (раздел 2.3 этого задания).

Проверка на каждую строку: если её убрать, агент начнёт ошибаться? Если нет — строка
уходит в правило или в документацию. Акцент вида «ВАЖНО» действует, только если
применён к одной строке в файле.

Локальных `AGENTS.md` в апках не делать: их роль выполняют правила с `paths`.

### 3.3 `.claude/rules/*.md`

Правила с ограничением области через `paths` во фронтматтере: такое правило
подгружается только когда агент читает или пишет файл, попадающий под glob.
Состав:

| Файл          | `paths`                                                   | Содержание                                                                                                                                                            |
| ------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server.md`   | `apps/server/**`                                          | Структура модулей вертикальными срезами, доступ к БД только через репозитории, явные транзакции, валидация на границе, запрет логировать токены                       |
| `contract.md` | `packages/contract/**`                                    | Схема добавляется раньше обработчика; типы выводятся из схем; изменение контракта требует правки клиента и документации в том же коммите                              |
| `client.md`   | `packages/api-client/**`, `apps/web/**`, `apps/mobile/**` | Обращения к API только через фабрику; ключи кеша не собираются руками; мутации объявляют инвалидацию                                                                  |
| `ui.md`       | `packages/ui-*/**`                                        | Стили только токенами; варианты в `ui-core`; парность имён и пропсов между `ui-web` и `ui-native`; на бесплатной ветке Uniwind нет `hover:` и `group-*`               |
| `i18n.md`     | `packages/i18n/**`, `apps/web/**`, `apps/mobile/**`       | Строки интерфейса живут в каталогах, а не в компонентах; русские формы множественного числа — четыре ключа; переменная счёта называется `count`                       |
| `admin.md`    | `packages/admin-kit/**`, `apps/web/src/routes/admin/**`   | Экраны строятся из реестра ресурсов; состояние таблицы в параметрах поиска; права через интерфейс поставщика, без прямых проверок; паритет с мобильным не применяется |
| `storage.md`  | `packages/storage/**`, `apps/server/src/**/files/**`      | Загрузка только подписанными формами POST; размер и тип ограничены политикой; настоящий тип проверяется по сигнатуре файла; контрольные суммы AWS отключены           |
| `queues.md`   | `apps/server/src/**/queue*/**`                            | Идемпотентность, лимит повторов, логирование начала и конца, падение задачи не роняет процесс                                                                         |
| `tests.md`    | `**/*.test.ts`, `**/*.test.tsx`                           | Проверяется поведение; внешние сервисы мокаются на границе; пороги покрытия не понижаются; в `apps/mobile` используется Jest                                          |
| `docs.md`     | `**/*.md`                                                 | Правила из раздела 14: структура страницы, стиль, запрещённые обороты                                                                                                 |
| `git.md`      | нет `paths`                                               | Conventional Commits, схема ветвления, одна работа — один pull request                                                                                                |

Нумерация правил не используется: подтверждений, что она помогает агентам,
в документации нет, а на ссылки проще брать имя файла правила.

### 3.4 `docs/BACKLOG.md`

Остаток работ, таблицы по статусам. Идентификатор —
**`B-<ГГММДД>-<короткий-слаг>`**: последовательная нумерация при параллельной
работе гарантированно даёт двум авторам один номер (раздел 7.6).

```markdown
## В работе

| ID                   | Заголовок                          | Тип  | Приоритет | Владелец | Где         | Критерий закрытия                  |
| -------------------- | ---------------------------------- | ---- | --------- | -------- | ----------- | ---------------------------------- |
| B-261008-redis-tests | Нет интеграционных тестов очередей | тест | средний   | владелец | apps/server | Тест с реальным Redis в CI зелёный |
```

Статусы `Открыто`, `В работе`, `Закрыто`; закрытые хранятся последними тридцатью,
с указанием коммита. Типы: `функциональность`, `тест`, `дока`, `рефакторинг`,
`инфраструктура`, `риск`. Пункт заводится в том же коммите, где обнаружена
недоделка, и обязательно содержит проверяемый критерий закрытия. Пункт в статусе
«В работе» обязан иметь владельца; в статусе «Открыто» владелец не требуется.

### 3.5 Главный механизм: блокирующий гейт

Официальная рекомендация — дать агенту проверку, которую он может запустить, и
закрыть работу хуком, а не советом в инструкции. Поэтому:

**`scripts/done-gate.sh`** — один скрипт, он же задача CI, он же хук `Stop`.
Начинается с `set -euo pipefail`. Порядок шагов — от быстрых к медленным, чтобы
агент получал обратную связь раньше:

1. `pnpm format:check`
2. `pnpm lint`
3. `pnpm typecheck`
4. `pnpm check:docs`, `pnpm check:backlog`, `pnpm check:env`, `pnpm check:parity`,
   `pnpm check:i18n`
5. `pnpm test:coverage`
6. `pnpm test:mobile` (если изменения касались `apps/mobile`)

Жёсткие правила, которые гейт проверяет дополнительно:

- появился новый пакет или приложение без страницы в `docs/` → падение;
- изменился `packages/contract` без изменений в `docs/` → падение;
- в `docs/BACKLOG.md` есть пункт без критерия закрытия → падение.

Предупреждения без падения: изменения в `apps/*/src` или `packages/*/src` без
единой правки в `docs/` — гейт называет затронутые области и продолжает.

Хук `Stop` запускает этот скрипт и при неудаче возвращает `exit 2`, передавая
причину в stderr: это единственный документированный способ не дать агенту
завершить работу. Два требования к сообщению: оно должно называть конкретный
проваленный шаг и команду для воспроизведения. У хуков `Stop` есть предел
подряд идущих блокировок, поэтому гейт обязан быть быстрым, а сообщение —
действенным, иначе агент начнёт буксовать.

**Бюджет времени — требование, а не пожелание.** Гейт на тёплом кеше укладывается
в полторы минуты. Если не укладывается, он делится на два: `pnpm gate` —
формат, линтер, типы, проверки и тесты затронутых пакетов; `pnpm gate:full` —
всё целиком, и этот вариант стоит в CI. Гейт на четыре минуты начнут обходить,
и механизм умрёт.

**Гейт работает без сети.** Ни одна его проверка не обращается к реестру,
к серверам MCP или в интернет: иначе он будет мигать на каждом обрыве связи
и доверие к нему исчезнет.

**Аварийный клапан.** Ситуация неизбежная: гейт блокирует из-за поломки, не
относящейся к текущей работе. Если выхода нет, хук отключат целиком, и это хуже
любого обхода. Поэтому гейт понимает переменную `GATE_ALLOW=<идентификатор пункта
бэклога>`: она пропускает **один названный** шаг, печатает это крупно в вывод
и требует, чтобы указанный пункт существовал в `docs/BACKLOG.md` со статусом
«Открыто» или «В работе». Проверяется в Фазе 3 намеренным использованием:
несуществующий идентификатор клапан не открывает.

Второй хук — `PostToolUse` на `Write` и `Edit`: форматирование затронутого файла.
Больше хуков не добавлять: событий в Claude Code более тридцати, и соблазн
обвесить ими всё приводит к шуму. Напоминания в принципе слабее гейта, поэтому
их роль здесь минимальна.

### 3.6 `.claude/skills/`

Скиллы — процедуры. Каждый — каталог с `SKILL.md`, до 500 строк, с фронтматтером,
где `description` и `when_to_use` вместе не длиннее 1536 знаков (дальше обрезается).
Скилл может нести свои скрипты и заранее разрешать их запуск через `allowed-tools`.

| Скилл                | Назначение                                                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `feature-workflow`   | Основной цикл: требование → схема контракта → тест → реализация → документация → бэклог → `pnpm gate` → коммит                                                                 |
| `module-integration` | Выполнение этапа ROADMAP по процедуре раздела 15                                                                                                                               |
| `api-endpoint`       | Добавление эндпоинта: контракт oRPC → обработчик Nest → использование в обоих клиентах → тесты → страница документации                                                         |
| `ui-component`       | Пара компонентов `ui-web` и `ui-native`: варианты в `ui-core`, одинаковые пропсы, обновление таблицы паритета                                                                  |
| `admin-resource`     | Добавление ресурса в админку: запись в реестре, колонки, фильтры, переопределения полей, права, демонстрационные данные, тесты экранов                                         |
| `bug-triage`         | Разбор отчёта из `.bugs/`: прочитать контекст, найти серверные логи по request-id, воспроизвести, написать падающий тест, починить, закрыть, перенести отчёт в `.bugs/closed/` |

### 3.8 `.claude/settings.json` и `.mcp.json`

`settings.json` коммитится; `settings.local.json` в `.gitignore`. Разрешения
вычисляются в порядке deny → ask → allow, первое совпадение выигрывает, и правило
`allow` не делает исключения из `deny`. Звёздочка ставится после подкоманды
(`Bash(pnpm run *)`). Запретить чтение `.env`, запись в `pnpm-lock.yaml` и
`git push --force`. Разрешения не должны перекрывать запуск гейта.

без подтверждения. По умолчанию один сервер: документация библиотек (Context7),
ключ через `${CONTEXT7_API_KEY}`. Он решает главную проблему агента в этом стеке —
сверку актуальных API вместо работы по памяти. Остальные (PostgreSQL, Playwright,
GitHub) описать в `docs/operations/mcp.md` как опциональные, с указанием, что для
базы нужен пользователь только на чтение, а работу с GitHub дешевле делать через
`gh`. Плагин из репозитория не собирать.

## Фаза 4. `apps/server`

**Цель:** API на Nest 12 с PostgreSQL, очередями, health-эндпоинтами и образом Docker.

### Работы

1. **Каркас Nest 12** на адаптере Express (D2). Nest 12 перешёл на ESM — проверить,
   что сборка и запуск настроены под ESM, и что это согласуется с `@orpc/nest`,
   который тоже ESM-only. Структура модулями-срезами:
   `module/{controller,service,repository,dto,tests}`.
   Глобально: фильтр исключений с единым форматом ошибки, интерсептор логирования
   с request-id, валидация на схемах из контракта.
2. **Конфигурация.** `@nestjs/config` плюс схема переменных на Zod: падение при
   старте с внятным сообщением, если переменная отсутствует. Все переменные —
   в `.env.example` и `docs/operations/env-vars.md`.
3. **Логи.** `nestjs-pino` с request-id в каждой записи. Проверить совместимость
   с Nest 12: на момент исследования в заметках к релизам `nestjs-pino`
   упоминания Nest 12 не было, поэтому peer-зависимости сверить и результат
   записать в ADR. Запрет на попадание токенов и персональных данных в логи
   закреплён правилом `server.md`.
4. **База данных: Prisma 7.9.x.**
   - Использовать `prismaSchemaFolder`: каждый будущий модуль получит свой
     `.prisma`-файл при общем журнале миграций. Сразу разложить схему по файлам,
     даже если их пока два.
   - Генерация клиента объявлена как задача turbo с `outputs`, чтобы попадала
     в кеш и не отваливалась в CI.
   - Доступ к данным только через репозитории, транзакции явные.
   - Скрипты `db:generate`, `db:migrate`, `db:deploy`, `db:studio`, `db:reset`.
   - **Процедура миграций при параллельной работе — раздел 7.3.** Здесь же
     добавить в CI проверку состояния миграций и соответствия схемы применённым
     миграциям: она ловит и забытую генерацию, и правку применённой миграции.
   - **Сиды, два набора.** `db:seed:demo` — данные для показа и ручной проверки
     (пользователи, несколько сущностей, пара файлов), `db:seed:test` —
     минимальный детерминированный набор для тестов. Оба идемпотентны и
     повторный запуск не ломает состояние. Это то, что делает демонстрацию
     живой, а тесты воспроизводимыми.
   - Демонстрационная сущность минимальная, чтобы показать срез
     «контракт → контроллер → сервис → репозиторий → миграция → тест».
   - На `TypedSQL` не опираться: в журнале изменений Prisma про него тихо
     с 2024 года.
5. **Очереди: BullMQ 6 через `@nestjs/bullmq` 11.**
   - Одна очередь-пример с продюсером и обработчиком; повторы с экспоненциальной
     задержкой; идемпотентность через детерминированный `jobId` плюс ключ
     идемпотентности, записываемый в Postgres в одной транзакции с побочным
     эффектом.
   - Расписания только через Job Schedulers (`upsertJobScheduler`). Помнить:
     опции `utc` больше нет (вместо неё `tz`), свой `jobId` задать нельзя
     (различать по имени задачи), а следующий запуск создаётся в момент начала
     обработки предыдущего.
   - Воркер — **отдельный процесс**: свой входной файл на
     `NestFactory.createApplicationContext` без HTTP-адаптера, скрипт
     `start:worker`, отдельная цель в Dockerfile.
   - `bull-board` за админским доступом, выключен по умолчанию.
   - Если позже понадобится атомарная постановка задачи вместе с коммитом строки,
     это делается не BullMQ, а отдельным механизмом на Postgres; записать как
     известное ограничение в `docs/apps/server.md`.
6. **Health: terminus 12.** API сменился — базового класса `HealthIndicator`
   и `getStatus()` больше нет, индикаторы пишутся через `HealthIndicatorService`
   с `check(key).up(data)` / `.down(data)`, цепочками `.withTimeout(ms)`
   и `.cacheFor(ms)`.
   - `/health/live` — **только процесс**: отзывчивость и потолок памяти.
     Внешних зависимостей здесь быть не должно: если проверка живости зависит
     от базы, короткий сбой Postgres приводит к перезапуску всех экземпляров
     и превращает устранимую аварию в неустранимую.
   - `/health/ready` — PostgreSQL, Redis, очередь. Готового индикатора Redis
     в terminus нет, писать свой. Применить `.cacheFor()`, чтобы трафик проверок
     не бил по базе. Для мягких зависимостей использовать статус `degraded`.
   - Помнить: исключение внутри индикатора даёт 500, а возврат `down` — 503.
   - `HEALTHCHECK` в Dockerfile указывает на `/health/live` и нужен для compose;
     в оркестраторе вместо него настоящие probes. Описать в
     `docs/operations/health.md`.
7. **Docker.** Многоступенчатый Dockerfile: слой зависимостей с кешем, сборка,
   финальный образ без dev-зависимостей, непривилегированный пользователь,
   `NODE_ENV=production`. Способ обрезки монорепозитория (`turbo prune` против
   `pnpm deploy`) выбрать и обосновать в ADR; оба рабочие, и их можно сочетать.
   `docker-compose.yml`: `postgres`, `redis`, `server`, `worker` в основном наборе,
   с томами, `healthcheck` и запуском после готовности зависимостей.
8. **Файлы: `packages/storage` и модуль на сервере.** Байты не проходят через API.
   - Адаптер ровно на четыре метода, и этот размер важен — именно он переживает
     смену поставщика:
     ```text
     createUploadTicket({ key, contentType, maxBytes })
       -> { url, fields, expiresAt }
     getDownloadUrl(key, ttlSec?)
     head(key) -> { size, contentType } | null
     delete(key)
     ```
   - Первая реализация — S3-совместимая, с `forcePathStyle: true` и
     **обязательно отключёнными контрольными суммами** (см. грабли). Эта же
     реализация обслуживает Garage в разработке и российских поставщиков
     объектного хранилища в продакшене.
   - Только **подписанные формы POST**: размер и тип ограничиваются политикой,
     входящей в подпись, и хранилище отвергает нарушение само. Подписанный PUT
     размер не ограничивает.
   - Привязка файла к сущности в два шага: запись со статусом ожидания → выдача
     талона на загрузку → загрузка клиентом → подтверждение → серверный `head()`
     для проверки настоящего размера и типа → перевод в готовое состояние.
     Размеру, заявленному клиентом, не верить; настоящий тип проверять
     по сигнатуре файла.
   - Уборка незавершённых загрузок — задача BullMQ по записям в ожидании.
   - В `docker-compose.yml` добавить S3-совместимое хранилище для разработки
     (**Garage**, не MinIO: он заархивирован) и интеграционный тест против него.
   - Проверка на вредоносное содержимое и обработка изображений в ядро не входят:
     оставить точки подключения и отправить в ROADMAP.
9. **Трассировка — только шов.** Подключение OpenTelemetry за флагом окружения,
   по умолчанию выключено, идентификаторы трассировки попадают в записи pino.
   Коллектор и поставщика в основу не закладывать: автоинструментации всё ещё 0.x
   и близок мажор 3.x.
10. **Тесты.** Unit на сервисы и обработчики очереди; интеграционные на контроллеры
    и репозитории против реальных PostgreSQL, Redis и хранилища (сервисные
    контейнеры в CI, локально через `docker:up`); тест, что `/health/ready`
    краснеет при недоступной зависимости, а `/health/live` остаётся зелёным;
    тест загрузки файла, включая отказ при превышении размера и при неверном типе.
11. **Документация.** `docs/apps/server.md`: структура, как добавить модуль,
    как работают миграции и очереди, как запускать локально и в Docker,
    известные ограничения.

### Точки разрыва сессии

Фаза крупная. Чистые точки: каркас с конфигурацией и логами (1–3), база данных
с миграциями и сидами (4), очереди (5), health (6), Docker и compose (7),
файлы (8), трассировка и тесты (9–10), документация (11). Каждая заканчивается
коммитом и зелёным гейтом.

### Критерии приёмки

- `pnpm docker:up`, затем миграции, затем `pnpm --filter server dev` поднимает API;
  `GET /health/ready` отвечает 200 со статусами зависимостей.
- Остановленный Redis переводит `/health/ready` в ошибку, `/health/live` остаётся 200.
- Задача, поставленная в очередь, обрабатывается воркером; это проверено тестом.
- Файл загружается по подписанной форме мимо API; попытка превысить размер
  или подменить тип отвергается **хранилищем**, а не только приложением.
- Интеграционный тест против поднятого в compose хранилища проходит — он же
  страхует от регрессии с контрольными суммами AWS SDK.
- `docker compose up --build` поднимает стек с нуля на чистой машине.
- `pnpm gate` зелёный.

### 5.1 `packages/contract`

- Контракты oRPC на Zod 4: входы, выходы, ошибки, метаданные маршрутов.

- Там, где схема описывает поле формы, вид поля помечается через `.meta()`
  Zod 4 (`.meta({ widget: 'select', options })`): это же описание потом читает
  конструктор админки в Фазе 8.
- **Важно про версии:** стабильная ветка oRPC — v1, а документация на сайте уже
  v2 beta. Закрепить v1 в каталоге версий и читать документацию с этой поправкой;
  переход на v2 завести отдельным пунктом бэклога.
- OpenAPI порождается из тех же контрактов и публикуется в разработке.
- **Политика совместимости.** Пока у API нет внешних потребителей, ломающие
  изменения разрешены, но каждое перечисляется в журнале изменений контракта
  с датой и причиной. Версионирование вводится в тот момент, когда появляется
  первый потребитель, которого вы не контролируете. Записать это сразу, чтобы
  при появлении модулей аутентификации и прав не возникло спора.

### 5.2 Серверная сторона

- `ORPCModule.forRoot` и декоратор `@Implement` в Nest. Преимущество этого
  варианта: декоратор лишь привязывает маршрутные метаданные, поэтому guard'ы,
  pipe'ы и интерсепторы Nest продолжают работать обычным образом.
- Проверить, что требования oRPC к версии Nest соблюдены (часть возможностей
  требует Nest не ниже 11.2, ESM — не ниже 12).

### 5.3 `packages/api-client`

- Транспорт с инъекцией конфигурации: базовый адрес, получение и обновление токена,
  хранилище токена, обработчик `401`, таймауты, повторы, разбор ошибок
  в типизированный вид. Платформенные различия передаются снаружи, поэтому пакет
  работает и в вебе, и в React Native.
- Утилиты запросов через `createTanstackQueryUtils` из `@orpc/tanstack-query`:
  он выдаёт `queryOptions`, `infiniteOptions`, `mutationOptions` и построители
  ключей. Своего слоя поверх не писать.
- Требования: ключи кеша порождаются из описания маршрута; предзагрузка вне
  компонента доступна (нужна загрузчикам маршрутов и серверному рендерингу);
  мутации объявляют инвалидируемые ключи, инвалидация выполняется централизованно;
  ошибки приходят типизированными из контракта.
- **Перехватчик для багрепорта:** кольцевой буфер последних двадцати запросов
  (метод, путь, статус, длительность, request-id) с маскированием заголовка
  `Authorization` и тел с паролями. Буфер читается пакетом `devtools` в Фазе 9.
  Перехватчик включается флагом и в продакшене по умолчанию выключен.
- Тесты: типизация на тестовых вызовах, генерация ключей, инвалидация после
  мутации, поведение при `401`, маскирование в буфере.

### 5.4 `packages/devtools` — заготовка

В этой фазе создаётся только ядро типов и интерфейс приёмника отчётов, без UI:
полноценная реализация в Фазе 9, когда есть все три приложения.

### Критерии приёмки

- Добавление маршрута в контракт без реализации на сервере ломает сборку
  или тест (проверить, какой именно механизм это ловит, и записать в документацию).
- Один и тот же запрос используется в загрузчике маршрута веб-приложения
  и в компоненте мобильного без дублирования кода.
- OpenAPI отдаётся и соответствует контрактам.
- Есть `docs/packages/contract.md` и `docs/packages/api-client.md` с примером
  «добавляем эндпоинт от схемы до вызова в интерфейсе».

## Фаза 6. `apps/web` и `packages/ui-web`

**Цель:** веб-приложение на семействе TanStack с UI на shadcn поверх Base UI.

### Работы

1. **Каркас** на `@tanstack/react-start` (ветка 1.x) с файловой маршрутизацией
   `@tanstack/react-router`. Сборка — Vite **7**: на Vite 8 связка ломается.
   В `vite.config.ts` плагин `tanstackStart()` ставится **раньше**
   `@vitejs/plugin-react`.
2. **Связка с Query — по актуальному API.** `queryClient` создаётся внутри
   `getRouter()` (по запросу, не глобально), передаётся в контекст роутера,
   после чего вызывается `setupRouterSsrQueryIntegration` из
   `@tanstack/react-router-ssr-query`: он сам ставит провайдер, дегидратацию
   и гидратацию. Руками `dehydrate`/`hydrate` при этом не делать.
   Контекст типизируется через `createRootRouteWithContext`.
3. **Загрузчики маршрутов.** Использовать `queryClient.query(opts)`;
   поведение прежнего `ensureQueryData` воспроизводится как
   `queryClient.query({ ...opts, staleTime: 'static' })`. В компонентах —
   `useSuspenseQuery` с тем же объектом опций. Устаревшие `ensureQueryData`,
   `fetchQuery`, `prefetchQuery` и `routerWithQueryClient` в коде не появляются;
   добавить правило линтера, которое их запрещает.
4. **Tailwind 4** через плагин для Vite. CSS-вход импортирует `tailwindcss`,
   затем `@<scope>/tailwind-config/theme.css`, затем `base.css`; директивой
   `@source` перечисляются каталоги исходников `packages/ui-web` и
   `packages/ui-core`. Тёмная тема — через `@custom-variant` и атрибут
   на корневом элементе.
5. **UI.** Инициализировать shadcn с поддержкой монорепозитория
   (`init --monorepo`, шаблон для TanStack Start), Base UI идёт по умолчанию,
   флаг `-b radix` не использовать. Компоненты складываются в `packages/ui-web`,
   алиасы в `components.json` указывают туда. Своя `components.json` нужна каждой
   рабочей области, а `style`, `iconLibrary` и `baseColor` обязаны совпадать.
   Учесть, что утилита `cn` переехала в отдельный пакет. Из-за открытых ошибок
   CLI в монорепозиториях делать коммит перед каждым `add` и проверять, куда
   попали файлы.
6. **Данные.** Только через `@<scope>/api-client`; прямые `fetch` в компонентах
   запрещены правилом линтера.
7. **Локализация.** Подключить `@<scope>/i18n`; язык определять по cookie,
   а не по сегменту пути: при серверном рендеринге cookie читается серверной
   функцией, и не приходится протаскивать параметр языка через каждый маршрут.
   Переключатель языка, формат даты и числа через обёртки пакета. Строк,
   вшитых в компоненты, не остаётся — это проверяется правилом `i18n.md`
   и скриптом.
8. **Загрузка файлов.** Компонент загрузки в `ui-web`: получает талон
   из контракта, отправляет файл подписанной формой POST напрямую в хранилище,
   показывает прогресс, подтверждает загрузку. Ошибки хранилища (превышение
   размера, неверный тип) показываются внятно.
9. **Место под админку.** Группа маршрутов `/admin` создаётся здесь пустой
   и с ленивой загрузкой, чтобы в Фазе 8 конструктор просто встал на готовое
   место и код админки не попадал в основную сборку.
10. **Docker.** Пресет `node-server`, запуск собранного вывода узлом; образ
    от непривилегированного пользователя, добавлен в compose отдельным профилем.
11. **Тесты.**
    - Vitest 5 с DOM-окружением плюс `@testing-library/react` 16.3.x: рендер
      ключевых экранов, работа фабрики с подменой сети, светлая и тёмная темы,
      состояние ошибки маршрута, переключение языка.
    - Для компонентов, где важны настоящие фокус, позиционирование и слои
      (всплывающие элементы Base UI), использовать браузерный режим Vitest
      с провайдером Playwright: провайдер на WebdriverIO в версии 5 удалён.
    - Сквозной тест на Playwright: сборка, запуск собранного сервера, один сценарий
      «открыть приложение и увидеть данные из API». Отдельная задача, в гейт
      не входит.
12. **Документация.** `docs/apps/web.md`: структура маршрутов, где что лежит,
    как добавить страницу с загрузкой данных, как устроена связка с Query,
    как работают язык и загрузка файлов.

### Критерии приёмки

- `pnpm --filter web dev` поднимает приложение; страница получает данные через
  фабрику, данные предзагружены на сервере.
- Смена значения токена в `packages/tailwind-config` меняет вид веба без правок
  в самом приложении.
- Переключение языка меняет интерфейс и форматы дат и чисел; выбор сохраняется
  между перезагрузками и учитывается при серверном рендеринге.
- Файл загружается из интерфейса напрямую в хранилище, минуя API.
- Сборка образа и запуск контейнера проходят.
- В коде нет устаревших API из пункта 3, это проверяется линтером.
- `pnpm gate` зелёный.

## Фаза 7. `apps/mobile`, `packages/ui-native` и паритет

**Цель:** мобильное приложение на том же фундаменте, со сборкой под веб,
и проверяемый паритет компонентов с вебом.

### Работы

1. **Каркас.** Expo SDK 57 (или новее, если вышел стабильный) с `expo-router`.
   Целевой режим разработки — **development build**, а не Expo Go: магазинная
   сборка Expo Go отстаёт от SDK, и документация Expo сама не рекомендует её для
   разработки продукта. Новая архитектура — единственная доступная, начиная с SDK 55.
   Структура каталога `app/` повторяет логику маршрутов веба там, где это осмысленно,
   но определения маршрутов между приложениями **не разделяются**: у Expo Router
   нет аналога загрузчиков, поэтому общий слой — это контракт, клиент и хуки.
2. **Монорепозиторий: ничего не настраивать.** С SDK 52 Metro конфигурируется
   автоматически, и документация Expo требует **удалить** `watchFolders`,
   `resolver.nodeModulesPath`, `resolver.extraNodeModules`,
   `resolver.disableHierarchicalLookup`, если они появились. Разрешение модулей
   для монорепозиториев включено по умолчанию с SDK 55. Проверить отсутствие
   дубликатов `react` и `react-native` (`pnpm why --depth=10`), при необходимости
   зафиксировать версии через `overrides` в корне.
3. **Uniwind, бесплатная ветка.**
   - Установка вместе с `tailwindcss` (поддерживается только Tailwind 4;
     для вариантов `active:`, `disabled:`, `focus:` нужен ≥4.3.3).
   - `global.css`: `@import 'tailwindcss'`, `@import 'uniwind'`, затем токены из
     `@<scope>/tailwind-config/theme.css`, затем директивы `@source` на исходники
     `packages/ui-native` и `packages/ui-core` **путями относительно самого
     CSS-файла**.
   - `metro.config.js`: `withUniwindConfig` — самая внешняя обёртка; `cssEntryFile`
     строкой с путём от корня проекта; `dtsFile` в каталоге, попадающем в `tsconfig`.
   - CSS импортируется в `app/_layout.tsx`, а не в точке регистрации приложения.
   - Типы генерируются при запуске Metro — первый запуск сделать до проверки типов.
   - На бесплатной ветке нет `hover:` и `group-*`; в общих примитивах их
     не использовать. Если они понадобятся, это переход на платную Pro —
     отдельный пункт бэклога с оценкой.
4. **`packages/ui-native`.** Компоненты на Uniwind с теми же именами и пропсами,
   что в `ui-web`; варианты из `ui-core`. Стилизация остаётся за собственными
   примитивами: единственная связь с Uniwind — строки классов, поэтому возможный
   переход на другую реализацию Tailwind для RN не затронет прикладной код.
5. **Данные.** Тот же `@<scope>/api-client`; хранилище токена на
   `expo-secure-store` передаётся в конфигурацию клиента (ни AsyncStorage,
   ни незашифрованный MMKV для токенов не использовать). Мобильные настройки
   TanStack Query: `onlineManager` через `expo-network` или NetInfo с явным
   чтением начального состояния сети, `focusManager` через `AppState` с защитой
   по платформе, обновление при фокусе экрана. Персистентность кеша — решение ADR;
   кеш запроса аутентификации не персистить никогда.
6. **Локализация и полифилы — здесь прячется тихая ошибка.** Подключить
   `@<scope>/i18n`, язык определять через `expo-localization` с сохранением
   выбора. И главное: в Hermes на этой версии **нет `Intl.PluralRules`**,
   поэтому в самом начале точки входа, **до** инициализации локализации,
   импортируются `@formatjs/intl-locale` и `@formatjs/intl-pluralrules`
   из точек входа `/polyfill-force`. Без них i18next не падает, а молча
   разрешает только английские формы — то есть русская грамматика становится
   неправильной незаметно. Тест на множественные формы для русского языка
   обязателен именно в мобильном приложении, а не только в пакете.
7. **Загрузка файлов.** Новый классовый API `expo-file-system`: файл
   отправляется подписанной формой POST напрямую в хранилище. Псевдо-Blob
   из `{ uri, type, name }` не собирать и файлы в base64 не читать — расход
   памяти утраивается и крупные медиафайлы валят приложение. Старый
   `FileSystem.uploadAsync` объявлен устаревшим.
8. **Веб-развёртка.** Экспорт веб-сборки (`expo export -p web`), проверка, что
   Uniwind отдаёт стили в вебе. Dockerfile для раздачи статики и профиль в compose.
   В документации развести роли: `apps/web` — продуктовая веб-поверхность,
   веб-сборка мобильного — вторичная поверхность для быстрой выдачи того же
   интерфейса в браузере. Серверный рендеринг в Expo для веба находится
   в альфа-состоянии, в основу его не закладывать.
9. **Тесты: Jest, а не Vitest.** Это единственное отступление от общей системы
   тестов, и оно сознательное: Expo документирует только Jest с пресетом
   `jest-expo`, а единственный путь через Vitest — библиотека в бете с одним
   мейнтейнером и неполной проходимостью.
   - `jest-expo` плюс `@testing-library/react-native`. Учесть, что в 14-й версии
     `render` и `fireEvent` стали асинхронными и требуют Node 22.13+.
   - Запуск через `pnpm --filter mobile test`, задача turbo та же `test`,
     поэтому `turbo run test` остаётся единой точкой входа.
   - Общую логику выносить в пакеты, которые тестируются Vitest, чтобы поверхность
     Jest оставалась маленькой. Это требование, а не пожелание.
   - Сквозные сценарии — Maestro.
   - Границу «что чем тестируется» описать в `docs/guides/testing.md` вместе
     с причиной отступления.
10. **Паритет.** Таблица «компонент → есть в `ui-web` → есть в `ui-native` →
    расхождения» в `docs/packages/ui.md`, поддерживается `pnpm check:parity`.
11. **Документация.** `docs/apps/mobile.md`, включая раздел о граблях Uniwind
    и о том, почему Metro не настраивается руками.

### Критерии приёмки

- `pnpm --filter mobile start` запускает приложение на development build;
  экран получает данные через ту же фабрику, что веб.
- `pnpm --filter mobile build:web` даёт работающую веб-сборку со стилями.
- Смена токена в `packages/tailwind-config` меняет вид мобильного приложения.
- **Тест на русские множественные формы проходит в мобильном приложении**:
  «1 файл», «2 файла», «5 файлов», «21 файл». Если убрать импорт полифилов,
  тест падает — это и есть страховка от тихой ошибки.
- Файл загружается из мобильного приложения напрямую в хранилище.
- `pnpm check:parity` проходит; расхождения перечислены с причинами.
- `turbo run test` прогоняет и Vitest, и Jest.
- `pnpm gate` зелёный.

## Фаза 8. Админка: `packages/admin-kit`

**Цель:** переносимый конструктор административных экранов и его демонстрация
в `apps/web`. Переносимая часть — пакет; размещение у каждого проекта своё.

Выгода здесь почти бесплатная: контракт oRPC с Zod-схемами уже описывает ресурсы
в машинно-читаемом виде, поэтому списки и формы строятся из того же описания,
которым валидирует сервер. Правила проверки не расходятся между клиентом и API
по построению.

### 8.1 Реестр ресурсов

Описание ресурса связывает маршруты контракта с представлением:

```text
defineResource({
  name: 'note',
  routes: { list, get, create, update, remove },   // из packages/contract
  columns: [...],            // что показывать в таблице
  filters: [...],            // схема параметров поиска
  form: { overrides: {...} }, // переопределения полей
  permissions: { list: 'note:read', create: 'note:create', ... },
})
```

Поля формы выводятся из Zod-схем маршрута. Zod 4 поддерживает `.meta()`, поэтому
подсказку о виде поля удобно хранить рядом со схемой в контракте:
`.meta({ widget: 'select', options })`. Реестр полей сопоставляет тип Zod плюс
аннотацию с компонентом и падает на текстовое поле, если ничего не подошло.

**Честная граница возможностей, которую надо записать в документации:**
генерируется примерно восемьдесят процентов плоских форм, остальное пишется
руками через `overrides`. Причины конкретные: `.refine()` и `.superRefine()` —
непрозрачные предикаты без метаданных, поэтому межполевые правила не превращаются
в интерфейс и всплывают только при отправке; размеченные объединения требуют
перерисовки поддерева при смене различителя; вложенные объекты и массивы требуют
решений о раскладке, которых в схеме нет.

### 8.2 Таблица данных

- **TanStack Table v9.** Учесть смену API: `useReactTable` переименован в
  `useTable`, состояние переехало на TanStack Store (`table.state`, `table.store`),
  возможности стали подключаемыми. Для совместимости со старым API есть
  `useLegacyTable`, а `stockFeatures` возвращает поведение «всё включено».
- Таблица ничего не вычисляет сама: `manualPagination`, `manualSorting`,
  `manualFiltering`, а общее число строк приходит из ответа контракта.
- **Готовые примеры shadcn для v9 ещё догоняют**, и управляемое состояние через
  новые атомы не является прямой заменой прежнего. Поэтому свой компонент
  `DataTable` поверх Base UI, а не вставка рецепта.
- Состояние живёт в адресной строке: `validateSearch` на маршруте принимает
  **схему Zod 4 напрямую**, адаптер нужен только для Zod 3. Промежуточные
  обработчики: `retainSearchParams` сохраняет параметры между переходами,
  `stripSearchParams` убирает совпадающие со значением по умолчанию, чтобы
  ссылки оставались читаемыми. Проверенный результат идёт прямо в ключ запроса.
- Выбор строк, групповые действия, видимость колонок, общие состояния пустоты,
  загрузки и ошибки.

### 8.3 Формы

- **`react-hook-form` с `@hookform/resolvers`** (поддержку Zod 4 в резолверы
  добавил автор самого Zod). Выбор против TanStack Form сознательный: тот вышел
  в стабильную версию, но React Native в списке поддерживаемых платформ
  отсутствует, а состояние поддержки Zod 4 официально не закрыто. Для слоя,
  который может понадобиться и в мобильном приложении, это лишний риск.
- Та же схема, что валидирует на сервере; оптимистичное обновление и
  инвалидация через фабрику из `api-client`.

### 8.4 Макет и права

- Боковая навигация строится по реестру и фильтруется по правам.
- Гейтинг на трёх уровнях: пункт навигации скрыт, маршрут закрыт, действие
  недоступно.
- Модуль прав появится позже (M2), поэтому конструктор работает через
  **интерфейс поставщика прав** с заглушкой, которая разрешает всё в разработке.
  Когда M2 приходит, подключается настоящий поставщик без правок экранов.

### 8.5 Служебные страницы

Вход, 403, 404 и страница состояния системы (сводка по `/health/ready`,
версия сборки, состояние очередей). Это тот минимум, которого не хватает
в каждом проекте.

### 8.6 Журнал действий — в два шага

Просмотр журнала входит в конструктор сразу: таблица событий с фильтрами по
актору, сущности и времени. **Запись** событий на уровне репозиториев делается
с заглушкой актора, потому что настоящего «кто» до модуля аутентификации взять
негде. Полноценная привязка к пользователю — отдельный пункт ROADMAP после M1.

### 8.7 Размещение и демонстрация

Группа маршрутов `/admin` в `apps/web` с ленивой загрузкой, чтобы код админки
не попадал в основную клиентскую сборку. Демонстрация на показательной сущности
из Фазы 4: полный цикл списка, создания, изменения и удаления.

**Паритет на админку не распространяется.** Это веб-только часть, поэтому
`packages/admin-kit` вносится в список исключений `check-parity`, иначе проверка
начнёт требовать несуществующей мобильной пары.

### Точки разрыва сессии

Чистые точки: реестр ресурсов (8.1), таблица (8.2), формы (8.3), макет и права
(8.4–8.5), журнал действий (8.6), размещение и демонстрация (8.7).

### 8.8 Чужой опыт, который стоит прочитать до начала

React-Admin в феврале 2026 выпустил `ra-router-tanstack` и Shadcn Admin Kit —
админку, поставляемую **реестром компонентов**, а не зависимостью: компоненты
копируются в репозиторий и правятся на месте. Это ровно та модель поставки,
которая нужна `admin-kit`, и форма их интерфейса поставщика данных — проверенная
заготовка для слоя ресурсов. Перенимать стоит подход, а не зависимость: любой
готовый административный фреймворк хочет владеть загрузкой данных и
маршрутизацией, и в стеке, где это уже решено контрактом oRPC, он сделает
контракт второсортным. Отдельно отметить при оценке: у React-Admin часть нужных
компонентов относится к платной редакции, а Refine в январе 2026 разделился
на «Refine Core» и одноимённый продукт-конструктор.

### Критерии приёмки

- Показательная сущность управляется из `/admin` целиком: список с
  пагинацией, сортировкой и фильтрами, создание, изменение, удаление.
- Состояние таблицы читается из адресной строки: ссылка на отфильтрованный
  список открывается в том же виде у другого человека.
- Форма отвергает значение, которое отвергает сервер, и причина отказа
  показывается у поля.
- Добавление нового ресурса в реестр даёт рабочие экраны без написания
  разметки, а переопределение одного поля не требует переписывать форму.
- Заглушка поставщика прав заменяется на другую реализацию без правок экранов
  (проверяется тестом с двумя поставщиками).
- Код админки отсутствует в основной клиентской сборке (проверяется разбором
  состава сборки).
- Служебные страницы работают, страница состояния показывает данные `/health/ready`.
- `pnpm check:parity` проходит с `admin-kit` в исключениях.
- `pnpm gate` зелёный.

## Фаза 9. Багрепорт и инструменты разработки

**Цель:** кнопка «сообщить о проблеме» в вебе и мобильном, которая собирает контекст
сама и отдаёт отчёт в виде, пригодном для разбора агентом.

Смысл механизма: отчёт должен нести `request-id` последних запросов. Сервер
уже проставляет его в логи (Фаза 4), клиент уже носит (Фаза 5), поэтому по отчёту
находятся серверные логи конкретного запроса. Без этого любой отчёт сводится
к «не работает кнопка».

### 9.1 `packages/devtools`

- **Сбор контекста.** Обязательно: маршрут и параметры; версия и git SHA сборки;
  имя окружения; платформа, версия ОС, устройство, размер экрана, локаль;
  кольцевой буфер последних двадцати запросов из `api-client` (метод, путь, статус,
  длительность, `request-id`); буфер примерно двухсот записей логов с перехватом
  `console.error`/`warn`, необработанных исключений и отказов промисов; снимок
  состояния TanStack Query в урезанном виде — только ключ, статус, факт ошибки
  и время обновления.
- **Трейл действий.** Последние тридцать событий: переход по маршруту, нажатие
  на элемент с `data-testid` или `accessibilityLabel`, отправка формы.
  **Значения полей не записываются** — иначе в отчёт попадут пароли и
  персональные данные.
- **Маскирование — в ядре, не в вызывающем коде.** Заголовок `Authorization`,
  токены, тела запросов с паролями в отчёт не попадают никогда. Набор правил
  маскирования покрыт тестами.
- **Приёмники по одному интерфейсу** (та же схема адаптеров, что у биллинга
  и уведомлений):
  - `file` — **по умолчанию**: отправка на dev-эндпоинт сервера, который пишет
    markdown в `.bugs/`;
  - `github` — создание issue с метками, для передачи отчёта другому человеку;
  - `api` — запись в таблицу Postgres (реализуется, если понадобится).
- **Снимок экрана.** В мобильном — `react-native-view-shot`, нативный и честный.
  В вебе — кнопка «приложить снимок» по желанию, без автоматики: снимки DOM врут
  на внешних шрифтах, canvas и кросс-доменных картинках.

### 9.2 Интерфейсная часть

Плавающая кнопка и форма: краткое описание, шаги воспроизведения, ожидаемое
поведение. Компоненты парные — `ui-web` и `ui-native`, по правилам Фазы 7.
Рендерится только при включённом флаге.

### 9.3 Серверная часть

Dev-модуль с `POST /dev/bug-reports`, который пишет файл в `.bugs/`. Жёсткие
требования: модуль регистрируется только при соответствующем окружении,
в продакшен-образе эндпоинта нет вовсе, размер отчёта ограничен, имя файла
формируется сервером.

### 9.4 Задел под продакшен

Ядро пишется так, чтобы в продакшене можно было включить **урезанную форму отзыва
от пользователя**: только текст, маршрут и версия сборки, без логов, сети, трейла
и снимков. По умолчанию выключено, включается флагом. Полноценный приём отзывов
с модерацией и привязкой к аккаунту — пункт ROADMAP, а не этой фазы.

### 9.5 Замыкание на агента

- `.bugs/` в `.gitignore`: сырой отчёт — расходный материал на машине разработчика,
  и ему незачем попадать в историю вместе с возможными остатками данных.
  Долговечный след — пункт `B-NNN` в `docs/BACKLOG.md`, который создаёт агент
  по итогам разбора.
- Скилл `bug-triage` (Фаза 3) читает `.bugs/`, находит логи по `request-id`,
  воспроизводит, пишет падающий тест, починяет, закрывает пункт бэклога
  и переносит отчёт в `.bugs/closed/`.
- `docs/guides/bug-reports.md`: что собирается, что маскируется, как разбирать
  отчёт, как переключить приёмник.

### Критерии приёмки

- Нажатие кнопки в вебе и в мобильном создаёт файл в `.bugs/` с заполненным
  контекстом, включая `request-id` последних запросов.
- Тест подтверждает, что `Authorization`, токены и пароли в отчёт не попадают.
- Тест подтверждает, что в продакшен-сборке эндпоинт отсутствует, а кнопка
  не рендерится.
- Отчёт о заведомо сломанном запросе позволяет найти серверные логи по
  `request-id` — проверено вручную и описано в документации.
- `pnpm gate` зелёный.

## Фаза 10. Контейнеры и CI

**Цель:** репозиторий проверяется автоматически, образы воспроизводимы.

### 10.1 Docker

Dockerfile для `server` (две цели: API и воркер), `web`, `mobile` (статическая
веб-сборка). Общие требования: многоступенчатость, кеш слоёв зависимостей,
установка только нужных пакетов монорепозитория, непривилегированный пользователь,
`HEALTHCHECK`, базовые образы зафиксированы. `docker-compose.yml` с инфраструктурой
в основном наборе и приложениями в профилях, плюс
`docker-compose.override.yml.example`. Страница `docs/guides/docker.md`.

### 10.2 `.github/`

- **`actions/setup/action.yml`** — составное действие: Node нужной версии, corepack,
  установка зависимостей, кеш хранилища pnpm через штатный кеш `setup-node`.
  Кеширование задач отдать Turborepo, не собирать ключи руками.
- **`workflows/ci.yml`** — на pull request и push в `main`:
  - `checkout` с `fetch-depth: 0` — **обязательно**, иначе определение изменений
    молча деградирует до полной сборки;
  - задача `gate`: тот же `scripts/done-gate.sh`, что у агента (полный вариант,
    если он разделён), с сервисными контейнерами PostgreSQL, Redis и хранилища.
    **Эта задача — обязательная проверка для слияния**, и настройка защиты
    `main` на неё ссылается;
  - задача `migrations`: состояние миграций и соответствие схемы применённым
    миграциям (раздел 7.3);
  - задача `build`;
  - задача `boundaries`: `turbo boundaries`;
  - задача `e2e`: Playwright для веба;
  - `concurrency` с отменой устаревших запусков; `--affected` там, где это
    оправдано; переменные окружения, влияющие на сборку, объявлены в `turbo.json`,
    иначе возможны ложные попадания в кеш;
  - на событиях слияния очередью и тегах базу сравнения задавать явно.
- **`workflows/docs.yml`** — `pnpm check:docs` плюс проверка внешних ссылок
  (`lychee`) на изменённых страницах, и сборка сайта документации (пункт 10.3 ниже).
- **`workflows/docker.yml`** — сборка и публикация образов в реестр при теге
  или слиянии в `main`, с кешем слоёв.
- **`workflows/mobile.yml`** — веб-сборка артефактом на каждый pull request;
  нативная сборка по ручному запуску, с заготовкой под EAS.
- **`workflows/release.yml`** — по тегу: гейт, сборка, публикация образов,
  черновик описания выпуска.
- **`workflows/claude.yml`** — ответ агента на упоминание в pull request через
  `anthropics/claude-code-action@v1`. Файл коммитится, но все шаги условны по
  наличию секрета, чтобы форки не падали. В `docs/operations/ci.md` отметить два
  момента: токен подписки привязан к конкретному человеку, поэтому для общего
  использования нужен ключ API, и передача штатного токена GitHub приводит к тому,
  что на коммиты агента не запускается CI.
- **`PULL_REQUEST_TEMPLATE.md`** — чеклист из раздела 13 плюс поля «какие правила
  затронуты» и «какие пункты бэклога закрыты».
- **`ISSUE_TEMPLATE/`** — задача, дефект, этап модуля ROADMAP.
- **`CODEOWNERS`** и настройка обновления зависимостей (Renovate либо Dependabot):
  регулярное обновление поддерживает принцип «версии не хардкодим».
- **Удалённый кеш Turborepo** (раздел 7.7): токен и команда через переменные
  окружения, чтобы второй участник и CI не пересобирали то, что уже собрано.
  Выбор между бесплатным кешем Vercel и своим — в ADR.

### 10.3 Сайт документации

Закрытый сайт, который показывает, из чего состоит проект и за что отвечает
каждая часть. **Обязательное условие: страницы порождаются из репозитория,
а не пишутся руками.** Написанная руками карта модулей станет вторым описанием
того, что уже лежит в `docs/modules/*`, и разойдётся с ним через месяц —
это прямое нарушение принципа «один источник».

Что собирается:

- всё содержимое `docs/` как есть;
- **карта модулей** — из статусов `ROADMAP.md` плюс назначение из `docs/modules/*`:
  что реализовано, что в работе, что не начато;
- **граф пакетов и приложений** — из их `package.json`;
- **справочник API** — из OpenAPI, который и так порождается из контракта;
- покрытие по пакетам, открытые пункты бэклога, список ADR, таблица паритета,
  реестр переменных окружения (**только имена и назначение, никогда значения**).

Как устроено: генератор статики (при этом стеке логичен VitePress), сборка
в CI, деплой по SSH на отдельный поддомен, закрытие basic-аутентификацией.
Отдельный виртуальный хост и каталог, без общего рантайма с боевым сайтом:
инструмент разработки не должен расширять поверхность атаки продукта.

Чего этот сайт **не** делает: он не показывает состояние развёрнутой системы.
Это задача страницы состояния из Фазы 8.5 — другой читатель и другой срок жизни
данных. Смешивать их не надо.

### Критерии приёмки

- Пробный pull request проходит CI зелёным.
- Намеренное нарушение роняет соответствующую задачу; после проверки отменить.
- Гейт в CI и гейт у агента — физически один скрипт.
- Задача гейта настроена обязательной проверкой для слияния в `main`.
- Забытая генерация миграции роняет задачу `migrations`.
- Сайт документации собирается и разворачивается на поддомен, закрыт
  аутентификацией; карта модулей и граф пакетов порождены, а не написаны руками.
- На сайте нет ни одного значения переменной окружения.
- `docs/operations/ci.md` описывает каждый workflow и как читать падение.

## Фаза 12. Готовность к использованию и приёмка

**Цель:** убедиться, что из решения действительно получается новый проект,
а не только что оно само собирается.

### 12.1 Пороги и чистый лист

1. Зафиксировать пороги покрытия по фактическому состоянию с небольшим запасом
   в корневом конфиге Vitest (пороги задаются по шаблонам путей — на проект
   Vitest 5 их не поддерживает). Записать правило «пороги не понижаются»
   в `docs/guides/testing.md`, и отдельно: пороги поднимаются осознанно,
   отдельным коммитом, никогда попутно с функциональной работой.
2. **Проверка с чистого листа:** клонировать репозиторий в новый каталог и пройти
   `docs/guides/getting-started.md` буквально, ничего не домысливая. Каждое
   расхождение — правка документации.
3. Прогнать полный набор: гейт, `pnpm build`, `docker compose up --build`,
   веб-сборку мобильного, сквозные тесты веба, сценарий Maestro.

### 12.2 Создание проекта из коробки

Без этого решение остаётся показательным репозиторием, а не основой.

1. **`scripts/init-project.ts`** — переименовывает scope пакетов, меняет имя
   и описание в `package.json`, переписывает `README.md` под новый проект,
   удаляет показательные сущности и их миграции, обнуляет `docs/BACKLOG.md`
   и `docs/architecture/decisions/` (кроме решений о стеке), сбрасывает историю
   git. Скрипт идемпотентен и заканчивается прогоном гейта.
2. **Репозиторий помечается шаблонным** на GitHub, чтобы новый проект создавался
   кнопкой, а не копированием.
3. **`docs/guides/trimming.md` — как выкинуть лишнее.** Первое, что делают
   с коробочным решением в новом проекте: удаляют ненужное. Без инструкции это
   вырезают топором и ломают проверки. Описать по пунктам: как убрать мобильное
   приложение (и что при этом делать с `ui-native`, паритетом и `check-parity`),
   как убрать админку, как перейти на один язык (и что тогда проверяет
   `check-i18n`), как отказаться от файлов или очередей. Для каждого случая —
   какие проверки подправить, чтобы гейт остался зелёным.
4. **Судьба этого задания.** `BOILERPLATE_TASK.md` — спецификация постройки,
   и после постройки она становится историей. Перенести в
   `docs/architecture/original-task.md`, убрать упоминания из `AGENTS.md`
   и из корня. Иначе каждый новый проект унаследует две тысячи строк описания
   уже сделанной работы, и агент будет принимать её за текущие требования.
5. `LICENSE` и решение о лицензии; `README.md` корня объясняет, что это основа
   и как начать из неё проект.

### 12.3 Настоящая проверка: сквозная фича в новом проекте

Проверка «клонировать и запустить» слабая. Настоящая проверка коробочного
решения другая: **создать из него новый проект и провести одну функциональность
насквозь** — схема в контракте, обработчик на сервере, миграция, экран в вебе,
экран в мобильном, ресурс в админке, строки на двух языках, тесты на всех
уровнях, страница документации, пункт бэклога закрыт, гейт зелёный.

Замерить время. Если это день — решение работает. Если три дня — где-то
в фундаменте трение, и его надо найти и записать, а не объяснить усталостью.
Результат замера и найденные места трения записать в
`docs/architecture/overview.md`.

### 12.4 Завершение

1. Проверить `README.md`: что это, из чего состоит, как запустить за пять минут,
   куда идти дальше.
2. Просмотреть `docs/BACKLOG.md`: пункты актуальны, у каждого критерий закрытия
   и владелец там, где он нужен, блокеров нет.
3. Заполнить в `docs/architecture/overview.md` таблицу «требование задания →
   где выполнено» и схему решения.

## 13. Definition of Done и механизм согласованности

### 13.1 Чеклист завершённой работы

1. Код написан и соответствует правилам из `.claude/rules/`.
2. При изменении API схема в `packages/contract` обновлена первой, клиент
   и документация — в том же коммите.
3. Поведение покрыто тестами; пороги покрытия не понижены.
4. Линтер и проверка типов проходят; отключения правил снабжены причиной.
5. Документация обновлена: страница приложения или пакета, при необходимости
   гайд и `docs/operations/env-vars.md`; дата последней проверки обновлена.
6. Решение с альтернативами оформлено ADR.
7. `docs/BACKLOG.md` отражает реальность: закрытое закрыто, новое заведено
   с критерием закрытия.
8. При изменении компонентов обновлена таблица паритета.
9. Новые строки интерфейса добавлены в каталоги `packages/i18n` в оба языка,
   а не вшиты в компонент; для русского заданы все четыре формы числа.
10. `pnpm gate` зелёный локально.
11. Коммит по Conventional Commits; в pull request чеклист заполнен.

Этот чеклист живёт в `AGENTS.md` ссылкой и в шаблоне pull request текстом.

### 13.2 Четыре ступени, и почему они именно такие

Официальная рекомендация для агентов — дать проверку, которую можно запустить,
и закрывать работу хуком: инструкции носят совещательный характер, а хук
детерминирован. Отсюда порядок ступеней от слабой к сильной:

1. **Процедура** — скилл `feature-workflow` ведёт по шагам.
2. **Правило по месту** — файл из `.claude/rules/` подгружается ровно тогда,
   когда агент трогает соответствующий код, и не занимает контекст в остальное время.
3. **Одна команда** — `pnpm gate` объединяет все проверки, поэтому «проверить всё»
   стоит одно действие.
4. **Блокировка** — хук `Stop` не даёт завершить работу, пока гейт не сойдётся;
   CI не даёт слить pull request.

Напоминания в этой схеме отсутствуют сознательно: подтверждений, что печать
советов меняет поведение агента, нет, а императивные формулировки в
дополнительном контексте способны сработать против себя.

Отдельно стоят проверки, встроенные в код и не зависящие от дисциплины:
расхождение контракта и реализации, паритет компонентов, полнота документации,
описанность переменных окружения, формат бэклога, совпадение hex-зеркала
палитры с `theme.css`.

## 14. Правила документации

Документацию читают люди. Цель страницы — чтобы человек, впервые открывший
проект, смог сделать работу без расспросов.

### 14.1 Структура страницы

1. Блок «Зачем читать / Кому / Последняя проверка».
2. Что это и где находится.
3. Как устроено, затем как с этим работать.
4. Примеры, которые можно скопировать и запустить.
5. Частые ошибки и что они означают.
6. Ссылки на соседние страницы и на файлы правил.

### 14.2 Стиль

- Короткие предложения, активный залог, конкретные существительные.
- Нумерованные шаги для последовательностей, таблицы для сопоставлений.
- Термины вводятся один раз и дальше не меняются.
- Числа, пути и команды точные.
- Каждая страница отвечает на вопрос «что мне теперь сделать».
- Объём подчинён смыслу: сорок строк по делу лучше двухсот с повторами.

### 14.3 Запрещённые приёмы

`scripts/check-docs.ts` роняет гейт на следующем:

- Противопоставления-пустышки вида «это не X, а Y», «не просто X, а Y» —
  главный признак текста, написанного ради объёма.
- Оценочные усилители без содержания: «мощный», «гибкий», «современный»,
  «революционный», «бесшовный», «молниеносный».
- Вводные пустышки: «важно отметить», «стоит отметить», «давайте разберёмся»,
  «в этой статье мы», «в современном мире», «как известно».
- Эмодзи в заголовках.
- Абзацы-вступления, пересказывающие заголовок.
- Обещания без проверки: «работает отлично», «проблем не возникнет».

Список ведётся в `scripts/docs-forbidden.json` **на русском языке** и пополняется
по мере обнаружения. Готовые наборы для Vale (в частности `vale-ai-tells`
с правилом на контрастные конструкции) закрывают только англоязычный текст,
поэтому Vale подключается дополнительно и необязательно. Нужное исключение
помечается `<!-- docs-check: allow <причина> -->`.

### 14.4 Когда документация обновляется

- Появился пакет или приложение — появилась страница и запись в `docs/README.md`.
- Изменился публичный контракт, переменная окружения, команда запуска — правка
  в том же коммите.
- Принято решение с альтернативами — появился ADR.
- Страница перечитана и подтверждена — обновлена дата.

## 15. Процедура выполнения этапа модуля

Любой пункт ROADMAP выполняется по этой процедуре. Она же записана в скилле
`module-integration`.

### 15.1 Шаги

1. **Рамка.** Прочитать пункт ROADMAP, применимые правила и
   `docs/modules/<модуль>.md`. Сформулировать, что входит в этап и что явно нет.
2. **Исследование.** Подагентом `researcher` найти 3–5 решений, по каждому —
   строка таблицы по критериям 15.2. Источники: документация проекта, реестр,
   журнал изменений, открытые проблемы, лицензия. Отдельно проверить, не сменился
   ли у проекта статус: в этой области за 2025–2026 годы несколько заметных
   библиотек были свёрнуты, перелицензированы или куплены.
3. **Решение.** Выбрать: готовое решение, готовое с адаптером или своя реализация.
   Оформить ADR с таблицей вариантов, выбором, последствиями и датой.
4. **План.** Разбить на 3–7 проверяемых шагов, завести пунктами бэклога.
5. **Ядро.** Реализовать в `packages/<модуль>` платформенно-независимую часть
   и подключить в `apps/server`. Публичный интерфейс — через `packages/contract`.
6. **Интерфейсы.** Добавить предусмотренный этапом минимум в веб и мобильное
   через общую фабрику и парные компоненты.
7. **Тесты.** Unit на ядро, интеграционные на серверную часть, сценарные
   для интерфейсов.
8. **Документация.** `docs/modules/<модуль>.md` переводится из «не реализовано»
   в описание устройства, схемы данных, точек расширения и примеров. Обновляются
   `docs/operations/env-vars.md` и гайды.
9. **Закрытие.** Обновить статус этапа, закрыть пункты бэклога, прогнать гейт,
   вынести оставшееся в новые пункты.

### 15.2 Критерии сравнения библиотек

| Критерий              | На что смотреть                                                              |
| --------------------- | ---------------------------------------------------------------------------- |
| Лицензия              | Совместимость с коммерческим использованием; не сменилась ли недавно         |
| Статус проекта        | Не свёрнут, не куплен, не переведён в режим «только критические исправления» |
| Активность            | Дата последнего выпуска, частота, реакция на проблемы                        |
| Зрелость              | Стабильный мажор; история ломающих изменений; число зависимостей             |
| Автобусный фактор     | Сколько людей реально коммитят                                               |
| Типизация             | Типы в составе, строгость, выводимость                                       |
| Совместимость         | Nest 12 и ESM, React Native, монорепозиторий, целевые версии Node            |
| Данные                | Нужна ли своя схема, как устроены миграции, уживается ли в общей базе        |
| Автономность          | Можно ли развернуть у себя; работает ли без внешнего сервиса                 |
| Платёжная доступность | Можно ли оплатить сервис из России, если он платный                          |
| Стоимость выхода      | Прячется ли решение за своим интерфейсом                                     |
| Размер                | Влияние на клиентскую сборку                                                 |

Правило выбора: при сопоставимых вариантах предпочитается тот, который прячется
за собственным интерфейсом и допускает замену. Решение, пронизывающее код
проекта, требует отдельного обоснования.

### 15.3 Общие требования ко всем модулям

- Ядро не зависит от конкретного поставщика услуги; поставщики подключаются
  адаптерами по одному интерфейсу.
- Модуль переживает перезапуск: состояние в PostgreSQL, фоновая работа в очередях.
- Внешние вызовы идемпотентны и защищены таймаутами.
- Модуль выключается флагом конфигурации и в выключенном состоянии не мешает.
- Публичные события модуля описаны, чтобы другие модули подписывались,
  не зная о нём.

## 16. ROADMAP: состав модулей

`ROADMAP.md` строится по шаблону. Для каждого этапа:

```markdown
### M<номер>.<этап> <название>

- **Статус:** не начат | в работе | выполнен
- **Зачем:** одна фраза о пользе.
- **Входит:** список.
- **Не входит:** список — защита от расползания объёма.
- **Точки интеграции:** server / web / mobile — что именно появится.
- **Кандидаты на анализ:** список с пометкой «проверить статус».
- **Критерии приёмки:** проверяемые пункты.
- **Процедура:** раздел 15 задания, скилл `module-integration`.
```

Кандидаты ниже собраны на 2026-10-07 и служат отправной точкой. Статус каждого
проверяется заново на дату выполнения этапа.

### M1. Аутентификация

**M1.1 Базовый токен — своя реализация.** Непрозрачный токен доступа, выдаваемый
при входе. В базе хранится **хеш** токена. Продление за счёт активности: при
обращении срок сдвигается вперёд, при этом действует **абсолютный предел жизни
сессии**, после которого нужен повторный вход. Отзыв отдельной сессии и всех
сессий пользователя. Список активных сессий с устройством и временем последней
активности. Ограничение частоты попыток входа. Кеш проверки в Redis по хешу токена.

Почему своя реализация, а не готовая библиотека: better-auth 1.7.7 закрывает
почти всё, включая скользящее продление и список сессий, но спотыкается ровно
на двух требованиях — токен сессии хранится **в открытом виде**, и **абсолютного
предела жизни сессии нет** (скользящее продление может тянуть сессию
неограниченно). Плюс интеграция с Nest у него только силами сообщества.
Объём своей реализации — порядка четырёхсот строк, и она не оставляет прослойки
между кодом и Postgres.

Точки интеграции: сервер — модуль и guard; `api-client` — хранилище токена
и обработка `401` (заложено в Фазе 5); веб и мобильное — вход, выход,
восстановление сессии при запуске.

**M1.2 Рост способов входа.** Телефон с кодом из SMS, одноразовые коды, второй
фактор на TOTP, восстановление доступа, внешние поставщики. Каждый способ —
отдельный провайдер к единому ядру сессий. На этом этапе переход на **better-auth**
становится осмысленным: у него есть плагины под второй фактор, одноразовые коды,
телефон и passkey, официальный пакет для Expo и возможность задать свой отправщик
SMS. Решение принимается ADR этапа, с учётом двух названных расхождений.

**Кандидаты:** своя реализация (M1.1), better-auth (M1.2 и далее), `@nestjs/passport`
как основа для своего. **Исключены по результатам проверки:** Lucia свёрнута
в учебное пособие в марте 2025; Auth.js влился в Better Auth, а next-auth v5
третий год в бете. Отдельные системы идентификации (Keycloak, Ory, Zitadel,
Logto) для основы приложения избыточны; у SuperTokens не удалось подтвердить
состояние лицензий по компонентам на 2026 год — читать файлы лицензий самому.

**Критерии приёмки M1.1:** вход выдаёт токен; обращение к защищённому маршруту
продлевает сессию; по истечении абсолютного предела требуется повторный вход;
отзыв сессии немедленно закрывает доступ; в базе нет токена в открытом виде;
веб и мобильное переживают перезапуск с сохранённой сессией; всё покрыто тестами.

### M2. Права и роли

Модель: право — строка `ресурс:действие`, возможен уточняющий признак области.
Роль — именованный набор прав. Права назначаются пользователю напрямую и через
роли; итоговый набор — объединение, с явными правилами для запретов.

**M2.1 Ядро.** Свои таблицы (`permissions`, `roles`, `role_permissions`,
`user_roles`, `user_permissions`), вычисление плоского набора прав при входе,
кеш в Redis с версионным счётчиком для сброса, guard и декораторы на сервере,
сервис `can(user, 'ресурс:действие', объект?)`.

**M2.2 Управление** ролями и правами через API.

**M2.3 Права на экземпляры объектов.** Полиморфная привязка
(`subject_type`, `subject_id`, `user_id`, `permission`), выражается условиями CASL.
Решение о включении в более ранний этап принимается ADR: это сильно влияет
на модель данных и на стоимость проверки.

**M2.4 Отражение прав в интерфейсах.** Плоский набор прав приходит в данных
текущего пользователя; на клиенте функция проверки и компонент-ограничитель.

**Кандидаты:** **CASL 7.0.1** — единственный из рассмотренных с настоящей
историей шаринга на клиент (упаковка и распаковка правил), MIT, подходит под
модель «роли как наборы». node-casbin — работоспособен, но для ограничения
интерфейса неудобен. Cerbos — политика как код в отдельном сервисе, добавляет
сетевой вызов в горячий путь. OpenFGA и SpiceDB — брать, только если понадобятся
транзитивные связи вида организация → команда → проект; они навязывают модель
отношений и отдельное хранилище. **Исключены:** Oso в опенсорсе объявлен
устаревшим; Permify куплен FusionAuth и распространяется под AGPL.

**Критерии приёмки M2.1:** запрос без права получает 403; изменение прав влияет
на доступ без перезапуска; кеш сбрасывается при изменении; набор прав приходит
в данных текущего пользователя; есть тесты на объединение прав из нескольких
ролей и на прямое назначение.

### M3. Биллинг

Оркестратор платежей в API. В интерфейсы на первых этапах уходит минимум.
Сущности: продукт, план, цена, подписка, счёт, платёж, право на функциональность
по оплате, журнал событий.

**Факт, определяющий весь модуль:** Stripe, Paddle и Polar в роли продавца-посредника
для российского юридического лица недоступны. Поэтому первым реализуется
российский поставщик.

**M3.1 Ядро** без поставщиков, с тестовым адаптером. Интерфейс адаптера:

```text
createPayment(order, { amount, currency, idempotencyKey, returnUrl, saveMethod })
chargeSavedMethod(subscription, { amount, methodToken, idempotencyKey })
parseWebhook(rawBody, headers, sourceIp)   // затем всегда перезапрос платежа по id
getPayment(providerId) / refund(providerId, amount)
```

Права на функциональность — **своя таблица** (`user_id`, `feature`, `source`,
`expires_at`), в которую пишут только обработчики подтверждённых событий. Тогда
покупки в сторах, YooKassa и T-Bank питают одну модель доступа.

**M3.2 YooKassa.** Официального SDK для Node у YooKassa нет (есть PHP, Python,
Ruby, Java, .NET), поэтому REST напрямую: ключ идемпотентности заголовком,
basic-авторизация, сохранение метода оплаты для повторных списаний. Два
требования, которые легко пропустить: **уведомления подтверждаются allowlist'ом
по IP, а не подписью**, поэтому проверять источник и **обязательно перезапрашивать
платёж по идентификатору** перед любым действием; и для большинства сценариев
нужны данные чека по 54-ФЗ.

**M3.3 T-Bank** как второй адаптер: у него есть поддерживаемый TypeScript SDK
(`@jfkz/tinkoff-payment-sdk` 2.0.2, апрель 2026, MIT, небольшой — зафиксировать
версию или вендорить). Покрывает эквайринг, СБП и чеки.

**M3.4 Покупки внутри приложений.** Либо RevenueCat (бесплатно до 2500 долларов
отслеживаемого оборота в месяц, далее 1%; требует development build, не работает
в Expo Go), либо `expo-iap` без посредника — тогда проверку чеков, состояние
прав и сверку продлений пишете сами. Отдельно проверить, доступны ли выплаты
Apple и Google на ваш аккаунт разработчика: это самостоятельная проблема,
не решаемая кодом. Учесть, что репозиторий `expo-iap` переехал в монорепозиторий
`openiap`.

**M3.5 Подписки.** Ни один российский поставщик не даёт движка подписок, поэтому
расписание продлений — свой планировщик на BullMQ поверх `chargeSavedMethod`,
с журналом попыток и обработкой отказов.

**Исключены:** Lago (AGPL, и это заметно, если решение будет распространяться),
Kill Bill (платформа на JVM) — для начального объёма избыточны.

**Критерии приёмки M3.1:** состояние платежа переживает повторную доставку
уведомления; расхождение с поставщиком обнаруживается сверкой; право на
функциональность выдаётся и отзывается по состоянию оплаты; тесты на тестовом
адаптере покрывают успех, отказ, повтор и возврат.

### M4. Уведомления

Ядро: событие создаёт уведомление по шаблону, ядро выбирает каналы по настройкам
получателя, ставит задачи доставки в очередь, пишет журнал и повторяет неудачи.

**M4.1 Ядро и канал внутри приложения.** Таблицы шаблонов, уведомлений, доставок
(канал, статус, идентификатор у поставщика, попытки), настроек получателя и тихих
часов. Одна точка входа `notify(userId, templateKey, payload, { dedupKey })`:
разрешить настройки → учесть тихие часы (отложить, не выбрасывать) → уникальный
индекс по ключу дедупликации → по одной задаче BullMQ на канал. Интерфейс адаптера
канала: `send(recipient, rendered)` и `parseStatusWebhook(raw)`.

Почему своё ядро: Novu распространяется под MIT в основной части, но
самостоятельное развёртывание тянет MongoDB и пять сервисов, а облачная версия
означает подписку в валюте и внешнюю зависимость. Перечисленные требования
укладываются примерно в шестьсот строк поверх уже имеющихся Postgres и BullMQ.

**M4.2 Push.** Служба уведомлений Expo как основной путь: вы отдаёте
service-account JSON для FCM и ключ `.p8` для APNs, Expo раскладывает по
устройствам. **Известный разрыв:** FCM не доезжает на устройства без сервисов
Google (RuStore, Huawei), поэтому в ядре сразу нужен откат на канал внутри
приложения и SMS. Прямая работа с FCM и APNs оправдана при большом объёме или
необходимости тонко управлять приоритетами.

**M4.3 SMS.** Российские шлюзы (SMS.ru, SMSC.ru, SMS Aero): у них простые
HTTP-интерфейсы, а существующие npm-обёртки — крошечные и без релизов, поэтому
**писать свою обёртку на сотню строк**, не добавляя зависимость. Twilio для
российских номеров практически неприменим: двусторонние SMS не поддерживаются,
регистрация буквенных имён отправителя закрыта с июля 2024.

**M4.4 Электронная почта.** Resend или Postmark как первый адаптер; вторым
заложить Unisender Go, если доставляемость в российские ящики окажется низкой —
отечественные сервисы оптимизированы под Mail.ru и Яндекс, и оплата у них проще.

**M4.5 Настройки получателя, тихие часы, ограничение частоты** как отдельный этап.

**Критерии приёмки M4.1:** событие создаёт запись; доставка идёт через очередь
с повторами; журнал содержит результат по каждому каналу; уведомление внутри
приложения видно в вебе и в мобильном; тесты покрывают повтор, отказ канала
и дедупликацию.

### M5. Наблюдаемость

Автоматический сбор падений дополняет багрепорт из Фазы 9: там человек описывает
замеченное, здесь машина ловит стектрейс. Этапы: подключение сбора ошибок
(Sentry либо самостоятельно развёрнутый GlitchTip) в трёх приложениях с привязкой
к `request-id`; включение OpenTelemetry поверх шва, оставленного в Фазе 4, когда
автоинструментации выйдут из версий 0.x; панель здоровья и журналов.

### M6. Развитие заложенного

- **Журнал действий с настоящим актором.** Просмотр журнала есть в конструкторе
  админки с Фазы 8, но запись ведётся с заглушкой: до модуля аутентификации
  «кто» взять негде. После M1 — привязка событий к пользователю и сессии,
  хранение адреса и устройства, политика срока хранения.
- **Проверка файлов на вредоносное содержимое** (ClamAV отдельным процессом,
  задачей в очереди за адаптером) и **обработка изображений** (производные
  размеры через `sharp`, строго на воркере, не в обработчике запроса). Точки
  подключения оставлены в Фазе 4.
- **Возобновляемая загрузка** крупных файлов, если понадобится.
- **Приём отзывов от пользователей** в продакшене: модерация, привязка
  к аккаунту, ответы. Развитие задела из Фазы 9.4.

### M7. Прочее

- **TanStack AI** (`@tanstack/ai`): подключение, когда пакет выйдет из версий 0.x.
  Сейчас ломающие изменения случаются между минорами.
- **Переход на oRPC v2**, когда ветка станет стабильной.
- **Переход на TypeScript 7**, когда `typescript-eslint` перестанет
  предупреждать.
- **Оценка Uniwind Pro**, если понадобятся `hover:` и `group-*`.
- **Пересмотр выбора формы и таблицы**: TanStack Form стоит проверить заново,
  когда появится поддержка React Native и закроется вопрос с Zod 4; примеры
  таблиц shadcn для TanStack Table v9 — когда догонят.

## 19. Что считать провалом

Решение не принято, если верно хотя бы одно:

- `pnpm gate` требует ручных обходов или падает на свежем клоне.
- Хук `Stop` не блокирует завершение работы при падении гейта.
- Документация расходится с кодом в проверяемых местах.
- Веб и мобильное обращаются к API разными способами.
- Палитра продублирована в приложениях.
- `docs/BACKLOG.md` пуст при наличии известных недоделок.
- Версии зафиксированы текстом в разных местах и расходятся.
- Багрепорт собирает секреты или присутствует в продакшен-сборке.
- Русские формы числа в мобильном приложении неправильны (признак забытых
  полифилов `Intl`).
- Подписанная ссылка на загрузку не ограничивает размер файла.
- Код админки попадает в основную клиентскую сборку.
- Гейт обходят, а не исправляют: хук отключён, проверки закомментированы либо
  `GATE_ALLOW` стоит постоянно.
- Карта модулей на сайте написана руками и расходится с `docs/modules/*`.
- Из решения нельзя создать новый проект, не правя пути и имена руками.
- Модули ROADMAP реализованы частично, без этапов, тестов и документации.
